| Agent | `/api/v1/agent/` | 讨论记录/权重配置 |
| 交易 | `/api/v1/trade/` | 下单/持仓/记录 |

**HTTP 方法约定**：

### 2.3 错误码体系

**编码规则**：5位数字 `XXYYZ`

- `XX`：模块编号（HTTP状态码风格）
- `YY`：子模块/场景编号
- `Z`：具体错误序号

| 模块 | 编号范围 | 示例 |
|:-----|:---------|:-----|
| 公共错误 | 00000-09999 | 参数校验/服务不可用 |
| 认证模块 | 40100-40199 | Token过期/登录锁定 |
| 策略模块 | 40200-40299 | 策略参数无效/回测失败 |
| Agent模块 | 40300-40399 | 讨论超时/结果无效 |
| 交易模块 | 40400-40499 | 下单失败/仓位不足 |
| 行情模块 | 40500-40599 | 数据源异常/行情延迟 |
| 资产模块 | 40600-40699 | 同步失败 |
| 经验模块 | 40700-40799 | 匹配失败/冷启动 |
| 新闻模块 | 40800-40899 | 爬取失败 |
| 监控模块 | 40900-40999 | 服务异常 |

**公共错误码**：

| 错误码 | HTTP状态码 | 含义 |
|:-------|:----------|:-----|
| 0 | 200 | 成功 |
| 00001 | 400 | 请求参数校验失败 |
| 00002 | 401 | 未认证（缺少Token） |
| 00003 | 403 | 无权限 |
| 00004 | 404 | 资源不存在 |
| 00005 | 409 | 资源冲突（如重复创建） |
| 00006 | 422 | 请求格式正确但语义错误 |
| 00007 | 429 | 请求频率超限 |
| 00008 | 500 | 服务器内部错误 |
| 00009 | 502 | 上游服务不可用 |
| 00010 | 503 | 服务维护中 |

**各模块专用错误码在对应 DD-xx 文档中定义，此处仅定义公共部分。**

### 2.5 API 版本策略

- 当前版本：`v1`，路径中体现 `/api/v1/`
- 版本升级规则：
  - **兼容变更**（新增字段/端点）：不升级版本
  - **破坏性变更**（删除字段/改语义）：新增 `v2` 路径，`v1` 至少保留3个月

## 3. 数据库规范

### 3.1 命名约定

| 对象 | 规范 | 示例 |
|:-----|:-----|:-----|
| 表名 | `snake_case`，复数名词 | `daily_klines`, `fund_flows` |
| 字段名 | `snake_case` | `stock_code`, `created_at` |
| 主键 | `id`，`BIGSERIAL` | `id BIGSERIAL PRIMARY KEY` |
| 外键 | `{关联表单数}_id` 或 `{关联表单数}_code` | `stock_code VARCHAR(10) REFERENCES stocks(code)` |
| 布尔字段 | `is_` 前缀 | `is_st`, `is_suspended` |
| 时间字段 | `{动作}_at` | `created_at`, `updated_at`, `deleted_at` |
| JSON字段 | `{内容}_json` | `agent_scores_json` |
| 索引 | `idx_{表名}_{字段名}` | `idx_klines_code_date` |
| 唯一索引 | `uk_{表名}_{字段名}` | `uk_users_username` |

### 3.2 通用字段约定

每张表必须包含以下通用字段（除非有明确理由不包含）：

```sql
id          BIGSERIAL     PRIMARY KEY,       -- 自增主键
created_at  TIMESTAMPTZ   NOT NULL DEFAULT NOW(),  -- 创建时间
updated_at  TIMESTAMPTZ   NOT NULL DEFAULT NOW()   -- 更新时间
```

**软删除**：需要软删除的表增加 `deleted_at TIMESTAMPTZ`，查询时默认过滤 `WHERE deleted_at IS NULL`。

### 3.3 数据类型规范

| 语义 | PostgreSQL类型 | Python类型 | 说明 |
|:-----|:--------------|:-----------|:-----|
| 主键 | `BIGSERIAL` | `int` | 自增，避免INT溢出 |
| 股票代码 | `VARCHAR(10)` | `str` | 6位数字+可能的后缀 |
| 金额 | `NUMERIC(18,4)` | `Decimal` | 精度4位小数，绝不用FLOAT |
| 比例/百分比 | `NUMERIC(8,4)` | `Decimal` | 如 0.1234 = 12.34% |
| 时间戳 | `TIMESTAMPTZ` | `datetime` | 带时区，存UTC显示CST |
| 日期 | `DATE` | `date` | 纯日期 |
| 布尔 | `BOOLEAN` | `bool` | 不用 TINYINT |
| JSON | `JSONB` | `dict/list` | 用JSONB，支持索引 |
| 枚举 | `VARCHAR(20)` + CHECK | `str` (Enum) | 简单枚举用CHECK，复杂用PG ENUM |
| 长文本 | `TEXT` | `str` | 无长度限制 |

### 3.4 索引策略

```sql
-- 1. 主键自动索引，无需额外创建
-- 2. 外键字段必须建索引
CREATE INDEX idx_{table}_{fk_field} ON {table}({fk_field});

-- 3. 高频查询组合建复合索引（最左前缀原则）
CREATE INDEX idx_klines_code_date ON daily_klines(stock_code, date DESC);

-- 4. 部分索引（只索引有价值的数据）
CREATE INDEX idx_stocks_st ON stocks(is_st) WHERE is_st = true;

-- 5. 大表分区（>100万行考虑分区）
-- daily_klines: 按年分区
-- news: 按月分区
-- trades: 按年分区
```

## 4. 伪代码规范

### 4.1 伪代码语法

采用 Python 风格的伪代码，兼顾可读性和精确性：

```
# 注释用 # 开头
function 函数名(参数名: 类型) -> 返回类型:
    # 业务逻辑描述
    if 条件 then
        处理逻辑
    else
        其他逻辑
    end if

    for 元素 in 集合 do
        循环体
    end for

    return 结果
end function
```

### 4.2 伪代码中标记特殊语义

| 标记 | 含义 | 示例 |
|:-----|:-----|:-----|
| `[DB]` | 数据库操作 | `user = [DB] query User WHERE id = uid` |
| `[REDIS]` | Redis操作 | `[REDIS] SET key = value WITH TTL 3600` |
| `[MQ]` | 消息队列操作 | `[MQ] PUBLISH channel = "stop_loss" message = msg` |
| `[HTTP]` | 外部HTTP调用 | `[HTTP] POST url = "..." body = data` |
| `[LLM]` | LLM调用 | `[LLM] prompt = "..." model = "deepseek"` |
| `[LOG]` | 日志记录 | `[LOG] INFO "订单已提交" detail = order` |
| `[ASSERT]` | 断言/前置条件 | `[ASSERT] user.is_authenticated == true` |
| `[RAISE]` | 抛出错误 | `[RAISE] Error(40101, "Token已过期")` |
| `[WAIT]` | 等待/异步 | `[WAIT] for event with timeout = 30s` |
| `[CONFIG]` | 读取配置 | `max_retry = [CONFIG] "trade.max_retry"` |

### 4.3 伪代码精度要求

- **必须覆盖所有分支**：if/else 不允许只有 if 没有 else（除非 else 为空需显式标注 `# no-op`）
- **必须标注错误处理**：每个可能失败的步骤都需 `[RAISE]` 或 try-catch
- **必须标注并发/竞态**：涉及共享状态的操作标注锁或原子性要求
- **必须标注幂等性**：函数头注释标注是否幂等

示例：

```
# 幂等性：是（重复调用返回相同结果）
function validate_token(token: string) -> TokenPayload:
    [ASSERT] token is not empty

    payload = jwt_decode(token, secret = [CONFIG] "jwt.secret")
    if payload is invalid then
        [RAISE] Error(40101, "Token无效")
    end if

    if payload.exp < now() then
        [RAISE] Error(40102, "Token已过期")
    end if

    is_revoked = [REDIS] GET "token_blacklist:{payload.jti}"
    if is_revoked == "1" then
        [RAISE] Error(40103, "Token已撤销")
    end if

    return payload
end function
```

## 5. 认证与鉴权公共约定

### 5.1 JWT Token 结构

**Access Token（短期）**：

```json
{
  "sub": "admin",           // 用户名
  "exp": 1746000000,        // 过期时间（Unix时间戳）
  "iat": 1745913600,        // 签发时间
  "type": "access",         // Token类型
  "jti": "a1b2c3d4-..."     // 唯一ID，用于黑名单
}
```

| 属性 | 值 |
|:-----|:---|
| 有效期 | 24小时 |
| 存储 | 前端内存（不存localStorage） |
| 用途 | API请求鉴权 |

**Refresh Token（长期）**：

```json
{
  "sub": "admin",
  "exp": 1746432000,
  "iat": 1745913600,
  "type": "refresh",
  "jti": "f0e1d2c3-..."
}
```

| 属性 | 值 |
|:-----|:---|
| 有效期 | 7天 |
| 存储 | 前端 localStorage（HttpOnly Cookie 方案待评估） |
| 用途 | 续期 Access Token |

### 5.2 鉴权中间件逻辑

```
# 每个需鉴权的请求经过此中间件
function auth_middleware(request: Request) -> Request:
    path = request.path

    # 白名单路径（无需Token）
    whitelist = ["/api/v1/auth/login", "/api/v1/auth/init",
                 "/api/v1/auth/status", "/docs", "/redoc", "/openapi.json"]
    if path in whitelist then
        return request  # 放行
    end if

    # 提取Token
    auth_header = request.headers.get("Authorization")
    if auth_header is missing then
        [RAISE] Error(00002, "未认证")
    end if

    token = auth_header.remove_prefix("Bearer ")
    payload = validate_token(token)  # 调用 DD-01 定义

    # 注入用户信息到请求上下文
    request.user = payload
    return request
end function
```

### 5.3 Token 黑名单机制

```
# 登出/密码修改时撤销Token
function revoke_token(jti: string, exp: number):
    ttl = exp - now_timestamp()  # 剩余有效期
    if ttl > 0 then
        [REDIS] SET "token_blacklist:{jti}" = "1" WITH TTL ttl
    end if
    # Token过期后自动从Redis清除，不需要手动清理
end function

# 验证时检查黑名单（见 5.2 validate_token）
```

## 6. 模块间通信约定

### 6.1 通信方式矩阵

| 场景 | 通信方式 | 说明 |
|:-----|:---------|:-----|
| 前端 ↔ API Server | HTTP REST | 同步请求-响应 |
| API Server → Scheduler | 内存直调 | 同一进程，函数调用 |
| Scheduler → 止损监视器 | Redis Pub/Sub | 异步通知（止损条件变更） |
| 止损监视器 → 交易执行 | Redis Pub/Sub + HTTP回退 | 止损触发时通知 |
| 数据采集 → 数据库 | SQLAlchemy ORM | 数据写入 |
| Agent调度 → LLM | HTTP API | 异步调用 |
| 进程间心跳 | Redis Key + TTL | 服务发现/健康检查 |

### 6.2 Redis Pub/Sub 频道定义

| 频道名 | 发布者 | 订阅者 | 消息格式 |
|:-------|:-------|:-------|:---------|
| `stop_loss:update` | Scheduler | 止损监视器 | `{"type": "add/remove", "position_id": int, "condition": {...}}` |
| `stop_loss:trigger` | 止损监视器 | Scheduler | `{"position_id": int, "current_price": float, "trigger_time": ISO8601}` |
| `market:state_change` | Scheduler | 前端(WS) | `{"from": "bull", "to": "bear", "reason": "..."}` |
| `trade:executed` | 交易执行 | 前端(WS) + 经验库 | `{"trade_id": int, "action": "buy/sell", ...}` |
| `system:alert` | 监控模块 | 前端(WS) | `{"level": "warn/error", "message": "..."}` |

**消息公共字段**：

```json
{
  "id": "uuid-v4",           // 消息唯一ID
  "channel": "stop_loss:trigger",
  "timestamp": "2026-05-01T09:30:00+08:00",
  "payload": { ... }          // 频道特有数据
}
```

### 6.3 进程心跳与依赖

```
# 各进程启动后注册心跳
function register_heartbeat(process_name: string):
    [REDIS] SET "heartbeat:{process_name}" = "alive"
              WITH TTL 30  # 30秒超时
    # 每隔10秒刷新一次
    start_interval(10s, () => {
        [REDIS] SET "heartbeat:{process_name}" = "alive" WITH TTL 30
    })
end function

# API Server 启动时检查依赖
function check_dependencies():
    for dep in ["postgres", "redis", "scheduler"] do
        status = [REDIS] GET "heartbeat:{dep}"
        if status is missing then
            [LOG] WARN "{dep} 心跳丢失"
            return UNHEALTHY
        end if
    end for
    return HEALTHY
end function
```

## 7. 日志规范

### 7.1 日志级别与使用场景

| 级别 | 场景 | 示例 |
|:-----|:-----|:-----|
| DEBUG | 调试信息，开发阶段 | 请求参数、中间变量 |

## 10. 并发与事务规范

### 10.1 数据库事务

```
# 事务边界原则：最小化持有时间
function transfer_transaction():
    tx = [DB] begin_transaction()
    try:
        # 1. 业务操作（尽量短）
        [DB] update Account SET balance = balance - amount
        [DB] update Account SET balance = balance + amount
        [DB] insert TradeLog(...)

        # 2. 提交
        tx.commit()
    except:
        tx.rollback()
        [RAISE] Error(40401, "交易执行失败")
    end try
end function
```

**规则**：
- 事务内禁止外部调用（HTTP/LLM），外部调用放在事务外
- 只读操作用 `READ COMMITTED` 隔离级别
- 涉及余额/仓位的写操作用 `SERIALIZABLE` 隔离级别
- 单用户系统，并发冲突概率极低，但关键操作仍需加锁

### 10.2 分布式锁

```
# 使用 Redis 实现分布式锁
function acquire_lock(key: string, ttl: int = 30) -> bool:
    lock_key = "lock:{key}"
    acquired = [REDIS] SET lock_key = "locked" NX WITH TTL ttl
    return acquired == true
end function

function release_lock(key: string):
    [REDIS] DEL "lock:{key}"
end function

# 使用场景
# - 每日策略执行（防止Scheduler重复触发）
# - miniQMT下单（防止并发下单冲突）
# - 经验库匹配（防止重复计算）
```

### 10.3 幂等性保障

| 操作 | 幂等性策略 | 说明 |
|:-----|:----------|:-----|
| 下单 | 幂等键（client_order_id） | 相同key返回已有订单 |
| 数据采集 | 日期+股票代码唯一约束 | 重复数据INSERT失败忽略 |
| Token续期 | Refresh Token jti | 同一jti只续期一次 |
| 经验存储 | scenario_hash去重 | 相同场景不重复存储 |

## 8. PRD需求追溯规范

> 本节确保每条PRD强约束在DD文档中有明确的覆盖点和追溯路径。

### 8.1 追溯矩阵

详细设计目录下维护 `TRACE-MATRIX.md`，格式：

```markdown
| 追溯ID | PRD行号 | PRD原文摘要 | 约束级别 | 对应DD | DD章节 | 覆盖状态 |
|--------|---------|-------------|---------|--------|--------|---------|
| T-001  | L1781   | React 18+TS | 强      | DD-01  | 4.3    | ✅已覆盖 |
```

**字段说明**：
- **追溯ID**: `T-{3位数字}`，全局唯一，按DD文档分组（DD-00: T-001~T-019, DD-01: T-020~T-039, ...）
- **PRD行号**: `L{行号}`，标记PRD原文位置，便于快速定位
- **约束级别**: `强`(必须实现) / `软`(建议实现，可调整)
- **覆盖状态**: `✅已覆盖` / `⚠️部分覆盖` / `❌未覆盖`

### 8.2 DD文档内嵌追溯标记

在DD文档的关键设计决策处，必须标注PRD来源：

```pseudocode
# [PRD-T-064] 策略一粗筛：近60日跌幅>=20%
if decline_60d_pct >= 0.20 then  # PRD L207 强约束
    pass_coarse = true
end if
```

**格式规则**：
1. 函数/类级别的追溯：在函数注释首行标注 `[PRD-T-{ID}]`
2. 关键参数/阈值的追溯：行尾注释 `# PRD L{行号} {强/软}约束`
3. 复用决策的追溯：标注来源路径，如 `# fork from StockAgent hot_news.py`

### 8.3 DD编写前必覆盖清单

每个DD编写前，从 `TRACE-MATRIX.md` 过滤该DD对应的 `❌未覆盖` 和 `⚠️部分覆盖` 行，生成清单：

```markdown
## DD-05 编写前必覆盖清单

- [ ] T-125: L629 止损监视器独立进程
- [ ] T-126: L640 止损进程不读Agent分析结果
- [ ] T-128: L647 无绕过通道
...
```

**编写完成后**：更新 `TRACE-MATRIX.md` 中对应行的覆盖状态为 `✅`。

### 8.4 DD版本更新规则

当DD文档因PRD合规修复而更新时：
1. 版本号递增（V1.0→V1.1→V1.2）
2. 版本行增加更新说明（如：`V1.1 | 更新：2026-05-01 前端伪代码Vue→React改写`）
3. 在 `TRACE-MATRIX.md` 中将对应行的覆盖状态更新为 `✅`
