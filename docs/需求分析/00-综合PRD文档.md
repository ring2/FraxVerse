## 1. 产品概述

### 1.1 产品定位

本产品是一款面向个人投资者的 **A股全自动智能量化交易系统**，基于经验驱动型量化方法论，综合量价分析、资金流向、主力行为学、心理学、资本市场运作逻辑五个维度进行决策。系统通过深度整合成熟的开源项目核心能力，避免从零开发的高成本与高风险，同时借助经验闭环 Agent 实现自我进化的经验积累循环。

**品牌内核**：碎片宇宙（FraxVerse）——「交易修心、心念为碎片、宇宙为心之投影」。系统以宇宙为视觉隐喻：每一次交易决策都是一枚心念碎片，碎片聚合成星图（持仓），星图映射内心（经验库内观）。UI设计以深空宇宙为背景，粒子滑动特效象征心念的流动与聚合，交易的本质是一场向内的修行。

核心定位：**不是对抗信息不对称（机构的信息优势无法复制），而是通过严格执行的交易纪律，在公开信息基础上做出比大多数散户更理性的决策。** 你的真正优势不是信息，是纪律。系统的核心价值在于：管住手、不扛单、不情绪化交易——这些才是散户亏钱的真正原因。交易即修心，每一次纪律执行都是对内心的观照。

核心差异化：**区别于传统量化（纯量价统计），建立在深入理解资本市场运作的前提下，通过"经验积累→场景匹配→Agent讨论→反馈调参"的闭环，让系统越跑越聪明。经验库即"心之投影"——市场是内心的镜子，系统通过经验碎片不断内观、纠偏、进化。**

### 1.2 目标用户

| 用户类型 | 特征 |
|:---------|:------|

| **扩展用户** | 有成熟量化交易策略的个人投资者 |

| **扩展用户** | 偏好本地部署、策略私有化的量化开发者 |

### 1.3 产品目标

1. **降本提效**：通过借鉴成熟开源项目，将从零开发的工作量降低70%，核心策略自建，其余模块（回测引擎、多Agent框架、数据源、前端、任务调度）借鉴开源项目组装
2. **全自动化**：实现从数据采集→策略筛选→股票池生成→Agent分析→交易执行→复盘归档的全流程无人值守
3. **纪律执行**：通过独立止损进程、硬约束止盈、无绕过通道的架构设计，确保系统在任何情况下都严格执行交易纪律，不出现情绪化决策
4. **经验驱动**：系统越跑越聪明，每次操作归档为结构化经验，相似场景自动检索历史经验辅助决策
5. **自我进化**：配合Hermes Agent，对失败进行复盘总结，Agent feedback.log → 周度建议+人工审批调参 → 持续迭代
6. **多端体验**：美观现代化UI，同时支持PC端深度操作与移动端监控
7. **高适配性**：完美适配两套核心交易策略（周期底部量能异动 + 趋势动量低吸），以及"道"论主线行情判定

## 2. 需求背景与问题分析

### 2.1 用户核心痛点

| # | 痛点 | 说明 |
|:-|:-----|:------|
| 1 | **散户凭感觉交易** | 随手单、追涨杀跌、情绪化决策，缺乏纪律性 |
| 2 | **传统量化不接地气** | 纯量价统计因子无法捕捉政策驱动、主力意图、情绪变化等底层驱动力 |
| 3 | **策略效果难以持续** | 市场风格切换后策略失效，需要持续人工调参 |
| 4 | **开发成本高** | 从零搭建量化系统需编写回测引擎、交易接口、Agent等大量核心代码 |
| 5 | **全流程割裂** | 数据、回测、实盘、复盘相互独立，缺少统一的进化闭环 |
| 6 | **经验不可积累** | 每次交易的经验只存在于人脑中，无法系统化复用 |

## 3. 核心策略说明

> 策略详情请参考：[用户画像与交易记忆]（已固化在Hermes持久记忆）
> 此处仅列出策略在系统中的实现方式与模块设计。

### 3.1 市场状态自动机

**设计目标：** 明确定义四种市场状态及其转换条件，确保策略一和策略二不会冲突。

```
┌──────────┐  主线确认     ┌──────────┐
│ 非主线状态 │ ─────────→ │ 主线确认  │
│ (仓位0%)  │ ←───────── │ (策略二)  │
└──────────┘  主线衰退     └──────────┘
     ↑                            │
     │ 底部确认                   │ 趋势破坏
     ▼                            ▼
┌──────────┐  止跌确认     ┌──────────┐
│ 底部机会期 │ ←───────── │ 趋势上升期 │
│ (策略一)  │ ─────────→ │ (策略二)  │
└──────────┘  趋势启动     └──────────┘
```

**状态切换保护规则（新增 — 防止竞态条件）：**

| 规则 | 说明 | 目的 |
|:-----|:-----|:-----|
| **状态切换冷却期** | 状态切换后至少持有3个交易日才能再次切换 | 防止同日策略切换导致反复开平仓 |
| **多主线判定** | 最多2条主线并行，按资金集中度排序 | 解决多个板块同时达到主线标准的问题 |
| **震荡保护** | 3天内状态来回切换 → 进入"观望态"，不参与交易 | 防止快速震荡导致过度交易 |
| **切换日志强制记录** | 每次状态切换必须写入 `market_state_log` 表，含触发原因、切换时间、前后状态 | 可追溯、可复盘 |

**市场状态日志表（新增）：**

```sql
CREATE TABLE market_state_log (
    id              SERIAL PRIMARY KEY,
    date            DATE NOT NULL,
    from_state      VARCHAR(16) NOT NULL,  -- 底部机会期/主线确认/趋势上升期/非主线状态/观望态
    to_state        VARCHAR(16) NOT NULL,
    trigger_reason  TEXT NOT NULL,          -- 触发原因
    main_line_sector VARCHAR(32),           -- 当前主线板块（如有）
    created_at      TIMESTAMP DEFAULT NOW()
);
```

### 3.2 策略一：周期底部量能异动

**核心逻辑链：** 底部震荡磨低 → 暴力下杀 → 消息面无利空 → 洗盘vs出货判定 → 底部缩量止跌 → 轻仓试错 → 严格止损

### 3.3 策略二：趋势动量低吸

**核心逻辑链：** 主线行情核心个股形成趋势 → 上行中缩量下跌 → 底层驱动因素未被破坏 → 缩量为获利盘离场 → 低吸介入 → 仓位管理 + 严格止损

### 3.4 止损纪律

跌破止损线割肉 → 盘中重新站回止损线 + 分时量价确认可买回 → 次日继续下跌继续止损 → 趋势持续则视情况加仓/滚仓做T

## 3.5 股票筛选全流程（四层漏斗）

> 这是系统每日收盘后的核心执行流程，从全市场5000只到最终1-3只精选标的。

### 第一层：粗筛（规则引擎 — 可量化计算，不依赖LLM）

**目的：** 从全市场快速过滤，缩小候选范围到几十只。

**策略一「周期底部量能异动」粗筛条件：**

| 条件 | 量化标准 | 数据来源 |
|:-----|:---------|:---------|
| 底部区域 | 近60日跌幅≥20% | 日K线 |
| 暴力下杀 | 近5日内出现过单日跌幅≥5%的K线 | 日K线 |
| 市值范围 | 50亿~500亿（中小盘） | 基础信息 |
| 排除项 | 非ST、非次新股（上市≥180天） | 基础信息 |
| 流动性 | 日均成交额≥1亿 | 日行情 |

**策略二「趋势动量低吸」粗筛条件：**

| 条件 | 量化标准 | 数据来源 |
|:-----|:---------|:---------|
| 主线板块 | 板块资金集中度≥12%，连续2日 | 板块数据 |
| 多头排列 | MA5>MA10>MA20>MA60 | 日K线 |
| 趋势稳定 | ADX ≥ 25 | 日K线 |
| 缩量回踩 | 近3日内成交量<5日均量80%，跌幅<3% | 日K线 |
| 排除项 | 非ST、非次新股 | 基础信息 |
| 流动性 | 日均成交额≥3亿 | 日行情 |

**技术实现：** pandas对全市场数据做条件过滤，全部是确定性计算，无模糊判断。约100-200行代码。

### 第二层：多维度评分（规则引擎 — 可量化计算，不依赖LLM）

两个策略的粗筛结果取**并集**后，对每只候选股票计算多维度评分，分值作为后续Agent的参考输入。

**评分维度与权重：**

| 维度 | 权重 | 评分因子 |
|:-----|:----:|:---------|
| **量价维度** | 20% | 均线排列完整性、量价关系、ADX趋势强度 |
| **资金维度** | 25% | 主力资金净流入方向、CMF资金流向、大单占比 |
| **情绪维度** | 15% | 板块涨停家数占比、龙虎榜净额、舆情情绪 |
| **主力行为维度** | 25% | 暴力下杀后缩量止跌特征、洗盘vs出货模式识别 |
| **资本市场逻辑维度** | 15% | 板块政策赛道判断、近期驱动事件、估值分位数 |

**主力行为维度量化细则（注意：这部分后续需要长期迭代打磨）：**

| 判断维度 | 倾向洗盘（加分） | 倾向出货（减分） | 数据来源 |
|:---------|:----------------|:----------------|:---------|
| K线形态 | 大阴线后1-2日收小阳线/十字星 | 连续大阴线+盘中无抵抗 | 日K线 |
| 成交量 | 下杀日放量→次日急剧缩量（<60%） | 下杀持续放量（量>5日均量） | 日K线 |
| 价格位置 | 已跌20%以上（底部区域） | 已涨50%以上（高位区域） | 日K线 |
| 分时特征 | 盘中急跌后缓慢收回 | 单边下跌无承接 | 分钟K线 |
| 消息面 | 无明显利空 | 配合利好消息掩护出货 | 新闻/公告 |
| 大单行为 | 下跌中大单净流入 | 下跌中大单净流出 | 资金流向 |

**开发注意事项：**
- 主力行为维度是评分中最接近"艺术"的部分，**第一次写不可能精确**
- V1版本先用上面6个因子做一个简单的加权打分（每个因子±3分范围）
- 后续通过经验积累 + Agent反馈来迭代优化这个评分规则
- 这一层的定位是"评分参考"，不是"裁决"，即使不准确也不影响系统运行

每只股票总分 = Σ(维度分 × 维度权重)，按总分排序取前**10-15只**进入股票池。

**技术实现：** pandas + numpy 做多维度加权计算。约200-300行代码。

### 第三层：Agent深入分析（LLM驱动 — Fork TradingAgents 改造）

四位Agent对股票池中的每只股票逐一深入分析，每位Agent独立输出评分、支持理由、反对理由。

```
对于股票池中的每只股票 XYZ：

Agent 1（主线猎手）：
  输入：板块数据、政策新闻、近期驱动事件
  输出：{score: 85, buy: "商业航天列入十四五重点...", against: "..."}

Agent 2（资金侦探）：
  输入：资金流向、大单/小单分布、盘口数据
  输出：{score: 70, buy: "主力资金连续3日净流入...", against: "..."}

Agent 3（情绪捕手）：
  输入：新闻情绪、板块涨停家数、市场情绪数据
  输出：{score: 65, buy: "板块涨停占比25%...", against: "..."}

Agent 4（经验法官）：
  输入：经验库中与当前场景匹配的历史经验
  输出：{score: 80, confidence: 0.75, matched_exp: [...]}
```

**多轮讨论机制：** 四位Agent互相看到彼此的分析结果后，各自调整评分，经过2-3轮收敛。

**Agent输出校验与不收敛兜底（新增 — 防止Agent异常输出影响决策）：**

当Agent输出格式异常、评分极端或讨论不收敛时，需有兜底机制：

| 异常场景 | 兜底策略 |
|:---------|:---------|
| Agent评分不在0-100范围 | 标记为无效输出，该Agent对此标的不参与投票 |
| Agent反对理由为空 | 评分强制降为50分（证伪机制底线） |
| Agent给出极端评分（0或100） | 记录警告日志，评分保留但参与投票时权重减半 |
| 3轮后Agent评分仍分歧>30分 | 丢弃最高分和最低分，取中间值平均（trimmed mean） |
| 某个Agent持续给出极端评分（连续5次） | 自动降低该Agent权重50%，推送告警 |

```python
# Agent输出校验器
class AgentOutputValidator:
    def validate(self, output: dict) -> bool:
        # 1. 格式校验：score在0-100范围内
        if not (0 <= output.get("score", -1) <= 100):
            return False
        # 2. 反对理由不能为空（证伪机制底线）
        if not output.get("against_reasons"):
            return False
        # 3. 极端评分检测
        if output["score"] in [0, 100]:
            logger.warning(f"Agent {output['agent_name']} 给出极端评分")
        return True

    # 不收敛时的降级策略
    def handle_no_convergence(self, rounds: int, scores: list) -> Decision:
        if rounds >= 3:
            # 丢弃最高分和最低分，取中间值的平均
            trimmed = sorted(scores)[1:-1]
            return Decision(score=mean(trimmed), method="trimmed_mean")
```

### 第四层：加权投票 + 风控过滤 → 最终决策

```
每只股票总分 = Σ(Agent_i评分 × Agent_i当前权重)

权重动态分配（根据当前市场状态）：
  主线行情明确：主线猎手 35%, 资金侦探 25%, 情绪捕手 15%, 经验法官 25%
  震荡市/无主线：主线猎手 20%, 资金侦探 25%, 情绪捕手 20%, 经验法官 35%
  极端行情：风控一票否决

总分排序 → 取前3名

风控逐一检查：
  - 流动性检查：日均成交额 > 阈值
  - 拥挤度检查：因子拥挤度 < 48%
  - 仓位检查：单票 ≤ 总资金30%

输出最终决策：
  标的A | 仓位20% | 止损-5% | 止盈+10%
  标的B | 仓位10% | 止损-4% | 止盈+8%
```

**技术实现：** 纯Python逻辑，150-200行代码。

**止损执行架构（独立进程 + 无绕过通道）：**

止损是系统的第一安全底线，需从架构层面确保其不受任何其他模块影响：

```python
# 止损监视器 — 独立进程运行，不依赖Agent/策略引擎
# 文件：trade/stop_loss_monitor.py

进程A（主系统）：策略分析 + Agent讨论 + 下单决策
进程B（止损监视器）：每秒检查持仓止损条件 → 触发 → 直接执行卖出

两个进程之间有两条通信通道：
  1. 共享数据库中的止损条件表（启动时加载）
  2. Redis pub/sub 通知新开仓（盘中实时更新）
进程B不读取Agent分析结果，不读取新闻，不读取任何可能"影响判断"的数据
```

| 设计原则 | 说明 |
|:---------|:------|
| **止损进程独立** | `stop_loss_monitor.py` 跑在单独进程中，与主系统进程无关 |
| **Agent无权干涉** | 进程B不读取Agent的任何输出，Agent死机不影响止损执行 |
| **无绕过通道** | 系统界面中不设置"手动跳过止损"按钮，如需干预只能通过miniQMT终端操作 |
| **止损条件绑定** | 下单时同步写入止损条件，条件不写入不下单 |
| **止损后冷却期** | 止损卖出后，该标的进入**24小时冷却期**，期间不纳入候选池，冷却期内Agent可以复盘但不可以推荐买入 |
| **冷却期后入场** | 冷却期结束后如需重新买入，需走完整筛选流程（不能跳过） |
| **止损即归档** | 触发止损后立即写入经验库，不等收盘后再复盘 |
| **内存缓存条件** | 止损条件在启动时从PG加载到内存，盘中只读Redis价格，不每秒查PG（见下方优化说明） |

**止损监视器内存缓存优化（新增 — 避免每秒查PG的性能隐患）：**

```python
# 止损监视器优化方案：条件在内存，价格在Redis
class StopLossMonitor:
    def __init__(self):
        self.active_conditions = {}  # 内存中缓存的止损条件
    
    def on_startup(self):
        """启动时从PG加载所有active条件到内存"""
        self.active_conditions = db.query(
            "SELECT * FROM stop_conditions WHERE status='active'"
        ).to_dict()
    
    def on_new_position(self, condition):
        """新开仓时，接收Redis pub/sub通知更新内存"""
        self.active_conditions[condition.id] = condition
    
    def check_loop(self):
        """每秒只从Redis读价格，不查PG"""
        for cond in self.active_conditions.values():
            price = redis.get(f"price:{cond.stock_code}")
            if price <= cond.stop_price:
                self.execute_stop(cond)
```

> **优化理由：** 原方案止损监视器每秒查询PostgreSQL，盘中4小时=14400次查询/天。改为启动时加载+内存缓存+Redis pub/sub通知更新，盘中完全不查PG。

**技术实现：** 止损监视器使用独立Python进程启动，读取 `positions` 表中的 `stop_loss_price` 字段对比最新行情，触发时调用 `xttrade.order_stock` 执行卖出。约100行代码。

**止盈执行策略：**

```
阶梯止盈（默认模式）：
  到达止盈位1（+8%）→ 卖出50%
  到达止盈位2（+15%）→ 卖出30%
  剩余20%让利润奔跑，用MA5作为移动止盈线

移动止盈（价格持续上涨时）：
  以MA5作为移动止盈线，收盘价跌破MA5自动卖出剩余仓位
  MA5每日滚动更新
  当涨幅超过20%后，止盈线改为MA10（给更大波动空间）

止盈保护机制：
  止盈和止损一样是硬约束 → 触发即执行，不经过Agent讨论
  止盈后该标的进入12小时冷却期（比止损短，因止盈说明方向判断正确）
  冷却期结束后可重新进入筛选流程
```

**交易确认模式（新增 — 半自动 → 全自动渐进）：**

系统V1阶段不直接执行交易，而是输出交易建议，用户确认后执行。随着信任积累逐步开放全自动。

| 模式 | 适用阶段 | 行为 |
|:-----|:--------|:------|
| **建议模式（V1默认）** | 首3-6个月 | 系统生成完整交易计划 → 推送微信通知 → 用户确认后才下单 |
| **半自动模式（V2）** | 6-12个月 | 系统自动执行止损/止盈，但新开仓需用户确认 |
| **全自动模式（V3）** | 12个月后 | 系统全自动执行所有操作（可选） |

**建议模式下三种确认粒度：**

```json
// 粒度1：一键全部确认
// 推送 → 用户回复"确认" → 当日所有建议全部执行

// 粒度2：按标的确认
// 推送 → 用户回复"确认1,3" → 只执行第1和第3个建议

// 粒度3：手动修改再确认
// 用户可以直接修改建议的价格或仓位后确认
// 用户在微信上回复"修改第1只目标价15.00" → 系统更新建议
```

**模式切换机制：**
- 只能单向升级：建议模式 → 半自动 → 全自动，不可降级（防止误操作从全自动降到手动）
- 切换需通过设置页面操作 + 二次确认密码验证
- 全自动模式下仍保留「手动紧急停止」按钮，触发后立刻切回建议模式

**技术实现：** 新增 `trade_mode` 表存储当前模式，交易执行器读取该模式决定是否等待用户确认。建议模式下，订单状态默认为 `pending_confirm`，用户确认后变为 `pending_submit`。

### 4.4 AI Agents 层

#### 4.4.1 四位Agent角色

| Agent | 角色 | 核心任务 | 提示词来源 |
|:------|:-----|:---------|:-----------|
| **主线猎手** | 主线行情识别 | 识别主线行情、判定"道"是否存在、政策力度与落地进度分析、板块周期定位 | 你的道论 + 主线判定认知 |
| **资金侦探** | 资金行为分析 | Smart Money流向跟踪、主力意图识别（洗盘vs出货）、资金合力/集中度分析 | 你的主力行为学认知 |
| **情绪捕手** | 市场情绪分析 | 市场情绪与散户心理分析、贪婪/恐惧指数判定、消息面情绪归因 | 你的心理学认知 |
| **经验法官** | 经验匹配 | 检索历史相似场景经验、计算场景匹配度、评估经验适用性、给出Confidence评分 | 你的经验驱动认知 |

#### 4.4.2 多Agent讨论机制

```
1. 四位Agent各自分析股票池中的每只标的
2. 每位Agent输出：买入理由 + 反对理由（证伪机制）
3. 加权投票（权重根据当前市场状态动态调整）
4. 风控模块一票否决（流动性/回撤/拥挤度检查）
5. 最终输出：1-3只精选标的 + 仓位方案 + 止损方案
```

**Agent在线校准机制（新增 — 防止Agent产生系统性偏差）：**

每位Agent的推荐准确率需实时监控与自动校准，防止Agent因提示词偏差长期乐观/悲观而不自知。

| 校准项 | 说明 |
|:-------|:------|
| **推荐记录** | 每位Agent对每只股票的分析输出（买入/观望/回避）+ 预测评分 + 实际结果 |
| **滚动胜率** | 按最近20次推荐统计每位Agent的推荐准确率（推荐买入且涨了=正确，推荐买入且跌了=错误） |
| **自动权重校准** | 胜率<40% → 权重降低50%；胜率>70% → 权重提升20%（有上限，不超过初始权重的130%） |
| **校准时机** | 每次投票前执行权重校准，使用截止到昨日的数据 |
| **校准面板** | 前端Agent讨论页增加一栏，显示每位Agent的历史推荐记录和胜率走势图 |

**校准算法：**
```
Agent_i_有效权重 = Agent_i_基准权重 × 校准系数

校准系数：
  胜率 ≥ 70% → 1.3（提升）
  60% ≤ 胜率 < 70% → 1.1（微升）
  50% ≤ 胜率 < 60% → 1.0（不变）
  40% ≤ 胜率 < 50% → 0.7（降低）
  胜率 < 40% → 0.5（大幅降低）

校准系数上限1.3，下限0.3（防止完全失效的Agent仍占权重）
```

**新增数据表字段：** `agent_logs` 增加 `predicted_outcome VARCHAR`（预测结果: buy/hold/avoid）和 `actual_outcome VARCHAR`（实际结果: win/loss/pending）

#### 4.4.3 证伪机制

> 每个Agent必须同时输出买入理由和反对理由

| Agent | 买入理由示例 | 反对理由示例 |
|:------|:------------|:-------------|
| 主线猎手 | 商业航天政策持续落地 | 板块集中度连续2天下降，可能退潮 |
| 资金侦探 | 主力资金今日净流入 | 大单占比下降，小单上升，可能在出货 |
| 情绪捕手 | 市场情绪偏乐观 | 散户一致性过强(88%看多)，可能见顶 |
| 经验法官 | ADX30+缩量下跌模式胜率70% | 上次类似场景(2024.10)失败，因大盘环境不同 |

仅当 **买入理由总分 > 反对理由总分** 并超过阈值时，才开仓。

#### 4.4.4 Agent运行实现策略

> 本节点记录Agent层在工程实现层面的关键决策，供开发阶段直接参考。

**1. LLM模型选型策略**

| 场景 | 推荐模型 | 原因 | 预估成本 |
|:-----|:---------|:-----|:---------|
| 每日Agent分析（股票池15只×4Agent×2轮讨论） | **DeepSeek V3 / GLM-4 Flash** | 成本低、中文支持好、推理速度快 | ~100万token/月 ≈ 10-20元 |
| 关键决策（开仓/止损前的复核） | **Claude Sonnet / GPT-4o** | 判断准确性要求更高，值得多花几毛钱 | 用量极少，可忽略 |
| 提示词开发调试阶段 | **DeepSeek V3** | 低成本调试，迭代快 | 调试成本可忽略 |

**2. LLM调用架构（异步非阻塞）**

```
主流程（定时任务触发）
  │
  ├── (1) 粗筛+评分 → 股票池（秒级，同步）
  │
  ├── (2) Agent分析任务（异步，不阻塞主流程）
  │     └── asyncio.gather() 并发调用4个Agent × 15只股票
  │           ├── Agent 1 - 股票1  ← API调用
  │           ├── Agent 1 - 股票2  ← API调用
  │           ├── Agent 2 - 股票1  ← API调用
  │           └── ...（全部并发，总耗时约4-10分钟）
  │
  └── (3) 等待所有Agent分析完成后 → 投票+风控（同步）
```

**关键实现细节：**
- 使用 `asyncio` + `aiohttp` 并发调用LLM API，不要串行
- 设置合理的超时时间（单次调用建议60秒，超过则跳过该Agent对该标的的分析）
- LLM调用全部放在**后台任务**中执行，主进程不等待

**3. 超时与降级策略**

| 场景 | 处理方式 |
|:-----|:---------|
| 单个Agent对某只股票分析超时 | 跳过这只股票在该Agent上的分析，用其他Agent的评分加权 |
| 所有Agent分析全部超时/失败 | 降级到第二层（评分层）的排序结果直接作为决策依据 |
| 部分股票分析完成、部分失败 | 已完成的分析参与投票，失败的用评分层分值作为替补 |
| LLM API连续调用失败 | 自动降低请求并发数（退避策略），如持续失败则切换到提示词中的备用模型 |

**4. 提示词开发策略**

Agent提示词不追求一次到位，采用迭代式开发：

```
V1（第1周）：基于你的交易认知写出初版，跑历史数据看输出质量
    ↓ 反馈：太笼统？忽略了关键因子？
V2（第2周）：细化判断维度和评分标准
    ↓ 反馈：分值不合理？反对理由太薄弱？
V3（第3周）：增加证伪检查清单，提升反对理由质量
    ↓ 反馈：与真实市场情况对比是否有偏差？
V4（第1个月）：磨合后的稳定版本
```

**Agent输入结构优化原则（新增）：**

四位Agent的分析框架应区分"定量计算"和"定性判断"——定量（技术指标）已由评分层处理，Agent应聚焦定性判断。

| Agent | 应减少的输入（定量数据） | 应增加的输入（定性素材） |
|:------|:------------------------|:------------------------|
| **主线猎手** | 均线/成交量/ADX等技术数据 | 近期政策文件原文、行业新闻、板块资金集中度变化趋势、宏观数据 |
| **资金侦探** | 单日资金流向数值 | 近5日主力资金趋势、大单/小单比例变化方向、筹码分布变化描述 |
| **情绪捕手** | 涨跌幅百分比 | 板块涨停家数变化趋势、舆情情绪倾向、散户讨论热度描述、龙虎榜特征 |
| **经验法官** | 单条经验匹配分数 | 统计报告（按策略/板块/市场状态）、匹配经验的原因说明 |

**核心原则：**
```
评分层 → 做数学（谁的技术面最好）
Agent层 → 做判断（谁的逻辑最硬、故事最真）
不要用Agent算数学——它不如SQL快。不要让Agent读K线——评分层已经算好了。
```

**V2提示词迭代方向：**
- 主线猎手的输入中增加"最近一周的板块相关政策链接或摘要"
- 资金侦探的输入中删除逐日资金流向明细，改为5日趋势描述
- Agent看到的技术指标数据改为"评分层已算好的维度分"，而不是原始K线

```
1. 你的角色定义
   - 你是谁？在交易团队中负责什么？
   
2. 你需要分析哪些数据（输入说明）
   - 你会收到哪些字段的数据
   - 重点关注哪些指标
   
3. 你的分析框架（步骤化）
   - 第一步：先看什么
   - 第二步：再看什么
   - 第三步：综合判断
   
4. 输出格式要求
   - 评分（0-100分）
   - 买入理由（列举2-3条）
   - 反对理由（至少1条，证伪机制的核心）
   - 补充说明（可选）
   
5. 评分标准参考
   - 什么情况给85分以上（强烈推荐）
   - 什么情况给60-85分（可以考虑）
   - 什么情况给60分以下（不推荐）
   
6. 证伪检查清单
   - 至少从以下角度提出反对理由：
     - [与你的交易认知相关的角度1]
     - [与你的交易认知相关的角度2]
     - ...
```

### 4.5 风险监控模块

#### 4.5.1 舆情+风控联动

> 来源：PRD 4.5.1节（经过适配）

当检测到持仓标的出现舆情事件时，自动联动风控处置：

| 事件级别 | 触发条件 | 自动处置 |
|:---------|:---------|:---------|
| **重大利空** | 监管处罚、重大亏损、重组失败 | 1. 推送最高级别告警 2. 仓位上限降至0% 3. 下一可交易时段自动清仓 |
| **一般利空** | 业绩不及预期、行业利空 | 推送告警通知 + 仓位上限降低50% |
| **重大利好** | 业绩大增、订单大单、政策利好 | 推送提示 + 确认驱动因素是否仍在 |
| **一般利好** | 行业回暖、中性公告 | 推送提示，纳入Agent分析 |

#### 4.5.2 实时风控

- 实时监控账户回撤，触发阈值自动降仓/清仓
  - 单日回撤≥5% → 自动清仓50%
  - 单日回撤≥8% → 自动清仓所有仓位
- 监控因子拥挤度，高拥挤度自动暂停策略
- 监控极端行情（大盘单日跌幅≥5%），自动清仓暂停交易3日
- 监控策略有效性，胜率<50%连续3日自动暂停
- 监控miniQMT连接状态，断开自动重连

**暂停后的复苏路径（新增）：**

系统触发自动暂停后，不能只是"停了等人工处理"，需要明确定义重启条件：

| 暂停触发条件 | 说明 |
|:------------|:------|
| 连续亏损3笔 | 单笔亏损≥1%，连续3笔 |
| 单月回撤 > 8% | 账户净值从最高点回撤超过8% |
| 胜率 < 40% 连续5笔 | 最近5笔交易仅有≤2笔盈利 |

**暂停期间系统的动作（自动化执行，无需人工）：**

```
暂停触发
  →
  (1) 立即停止所有新开仓操作（已有持仓按止损/止盈规则正常处理）
  →
  (2) Agent离线分析失效原因：
      - 当前市场状态是什么？（震荡/主线/极端）
      - 最近N笔亏损交易的共性是什么？
      - 是否某条策略完全失效？某位Agent持续误判？
  →
  (3) 系统自动跑回测验证：
      - 用过去30天的数据重新跑当前参数 → 看收益曲线
      - 如果回测也亏 → 说明策略本身失效，非随机波动
  →
  (4) 生成分析报告 → 推送微信通知
```

**三种复苏路径：**

| 路径 | 条件 | 动作 |
|:-----|:-----|:------|
| **路径A（策略可修复）** | Agent分析出具体问题 + 回测证明新参数有效 | 自动调参 → 自动恢复交易 |
| **路径B（降级运行）** | Agent分析不出具体原因，但回测无异常 | 跳过Agent层，降级到纯规则模式运行 |
| **路径C（全停）** | 回测也亏，或Agent分析认为当前市场环境不适合策略 | 暂停交易7天，7天后重新冷启动评估 |

**路径A的具体流程：**
```
Agent分析结果 → 建议调整参数（如：放松松粗筛条件/收紧止损线）
  → 系统用建议参数跑过去30天回测
  → 回测结果达标（胜率>50% + 预期收益的80%以上）
  → 自动应用新参数 → 恢复交易
  → 记录本次调整到系统日志
  → （如果恢复后仍连续亏损 → 降级到路径B）
```

**路径B的具体流程：**
```
Agent层被跳过 → 仅用粗筛+评分+权重排序决定交易
  → 纯规则模式运行7天
  → 7天后系统评估：纯规则模式是否优于Agent模式？
  → 如果纯规则模式表现更好 → 建议长期关闭Agent层
  → 如果两者差不多 → 尝试重新激活Agent层
```

**路径C的具体流程：**
```
暂停交易7天
  → 期间系统只做数据采集和分析（不下单）
  → 7天后生成"市场状态变化报告"
  → 推送到微信："系统已暂停7天，当前市场状态为XXX，建议手动检查后重新启动"
  → 用户确认后重新进入冷启动评估流程
```

#### 4.5.3 新增风控规则

> 新增模块 — 对标行业标准的补充风控

| 风控规则 | 触发条件 | 自动处置 |
|:---------|:---------|:---------|
| **隔夜风险评估** | 外盘（美股/港股/商品）波动≥3%或政策突变 | 开盘前推送预警，降低隔夜仓位上限 |
| **盈亏比滚动监控** | 最近20笔交易盈亏比从1.5降到1.0以下 | 触发预警推送，不暂停交易但标记监控状态（注：盈亏比缓慢下降比胜率骤降更隐蔽，是策略逐渐失效的信号） |
| **最大连续亏损次数** | 连续亏损交易达到N次（默认5次） | 自动暂停策略，待Agent分析失效原因后恢复 |
| **交易对手风险** | miniQMT接口连续3次调用失败 | 停止所有下单操作，推送最高级别告警 |

#### 4.5.4 绩效分析

> 新增模块 — 按策略、市场状态分类统计

| 指标 | 计算方式 | 按维度拆分 |
|:-----|:---------|:-----------|
| 年化收益率 | 累计收益 / 运行天数 × 365 | 策略一/策略二分别计算 |
| 最大回撤 | 净值最高点到最低点的最大跌幅 | 主线行情期 / 震荡市分别计算 |
| **夏普比率** | (年化收益 - 无风险利率) / 年化波动率 | 策略一/策略二分别计算 |
| **卡玛比率** | 年化收益 / 最大回撤 | **最适配你"少回撤"追求** |
| 胜率 | 盈利交易笔数 / 总交易笔数 | 按策略、按市场状态分类 |
| 盈亏比 | 平均盈利 / 平均亏损 | 按策略分类 |
| 单笔最大亏损 | 逐笔分析最大亏损交易 | 记录原因供复盘 |
| 月度收益分布 | 每月的收益统计 | 判断收益稳定性 |
| 逐笔交易明细 | 每笔的入场/出场/盈亏/持有天数 | 可导出CSV |

**技术实现：** 基于交易日志表，用SQL聚合计算，前端用ECharts展示图表。

#### 4.5.5 分层回溯验证

> 新增模块 — 追溯系统每个环节的真实价值贡献

系统的决策链条为：`数据 → 规则评分 → Agent分析 → 投票 → 最终决策`。每层都可能引入误差，且越往后越难追溯。需要一个机制来验证每个环节是否真的创造了价值。

**各层输出独立存储：**

| 层级 | 存储内容 | 用途 |
|:-----|:---------|:-----|
| 粗筛层 | 入选的全部候选标的 + 排序 | 验证粗筛条件是否有遗漏 |
| 评分层 | 每只标的的五个维度评分 + 总分 | 验证评分权重是否合理 |
| Agent层 | 每位Agent的评分 + 买入/反对理由 | 验证Agent是否有系统性偏差 |
| 投票层 | 加权前后的排序变化 | 验证投票权重是否合理 |
| 最终决策 | 最终选出的标的 + 仓位方案 | — |

**回溯分析方法（事后执行）：**

```
一笔交易结束后（止盈/止损/手动平仓）：
  → 系统自动触发回溯分析
  → 模拟"如果只依赖某层决策"的结果：

  场景1：仅使用粗筛层结果（前3名直接买入）
    → 该笔交易会赚/亏多少？ → 记录到 decision_layer_trace 表

  场景2：仅使用评分层结果（评分排序前3直接买入）
    → 该笔交易会赚/亏多少？ → 记录

  场景3：仅使用Agent层结果（Agent评分前3直接买入）
    → 该笔交易会赚/亏多少？ → 记录

  场景4：实际决策 vs 各层模拟 → 生成对比报告
```

**月度贡献度报告格式：**
```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
📊 4月 系统各层贡献度报告
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

本月交易笔数：8笔（盈利5笔，亏损3笔）
胜率：62.5%

各层虚拟胜率对比：
  ├── 粗筛层：50.0%（4胜4负）
  ├── 评分层：62.5%（5胜3负）✅ 当前最优
  ├── Agent层：57.1%（4胜3负，跳过了一次Agent失败）
  └── 投票层：62.5%（5胜3负）→ 实际决策

各层贡献度分析：
  ├── 粗筛层 → 提供了正确的候选池，但排序不够精准
  ├── 评分层 → 本月表现最优，与Agent层结论不一致时建议优先参考评分
  ├── Agent层 → 上月准确率68%，本月下降至57%，建议检查提示词是否需要更新
  └── 投票层 → 权重未明显改善结果，建议微调基准权重

建议：
  - 主线猎手连续2个月准确率<50%，建议降低其权重
  - 评分层已连续3个月贡献为正，建议维持当前权重
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**噪声环节自动精简：**
- 如果某个层连续3个月贡献度为负（虚拟胜率 < 50% 且低于系统综合胜率）
- 系统应自动推送提示：建议关闭/调整该环节
- 例如：Agent层连续3个月跑输评分层 → 提示"Agent层可能引入噪声，建议暂时跳过或降低权重"

**新增数据表：** `decision_layer_trace`（存储各层回溯分析结果，包含日期、交易ID、各层虚拟盈亏、贡献度评分）

##### 4.6.2.3 安全机制

| 机制 | 说明 |
|:-----|:-----|
| **登录限次** | 同一IP连续5次登录失败后锁定15分钟，返回429 Too Many Requests；锁定计数存Redis，key: `login_fail:{ip}` |
| **密码强度** | 最少6字符，无其他限制（个人系统，不强求复杂密码） |
| **密码存储** | bcrypt加密（cost factor=12），数据库中不存明文 |
| **Token安全** | Access Token仅存内存（不存localStorage，防XSS）；Refresh Token存localStorage（仅勾选"记住我"时） |
| **JWT签名** | HS256算法，密钥从环境变量 `JWT_SECRET` 读取，最少32字节随机字符串 |
| **会话管理** | 同一用户仅允许1个活跃会话；新登录自动使旧Token失效（Redis记录当前有效token的jti） |
| **HTTPS** | 生产环境强制HTTPS，Docker Compose配置nginx反向代理 + Let's Encrypt |

##### 4.6.2.6 Token 续期前端实现规范

```
前端请求拦截器逻辑（axios interceptor）：

1. 请求拦截器（Request Interceptor）
   → 每个请求自动附加 Authorization: Bearer {accessToken}

2. 响应拦截器（Response Interceptor）
   → 收到 401 响应
   → 检查是否有 Refresh Token
     ├── 无 → 跳转 /login
     └── 有 → 调用 POST /api/v1/auth/refresh
              ├── 成功 → 更新内存中的 accessToken
              │         → 用新 Token 重发原请求（最多重试1次）
              └── 失败 → 清除所有 Token
                         → 跳转 /login
                         → 显示提示："会话已过期，请重新登录"

3. Token 刷新竞态处理
   → 多个请求同时401时，仅发起1次refresh请求
   → 其他请求排队等待refresh结果后统一重发
   → 实现方式：全局Promise锁（refreshPromise变量）

4. 路由守卫
   → beforeEach 检查：
     ├── /login, /setup → 已登录则跳转 /dashboard
     ├── 其他页面 → 未登录则跳转 /login
     └── /setup → 检查users表是否为空，非空则跳转 /login
```

##### 4.6.2.8 数据库表设计

```sql
-- 用户表（单行记录，个人系统仅一个管理员）
CREATE TABLE users (
    id          SERIAL PRIMARY KEY,
    username    VARCHAR(20) NOT NULL UNIQUE,
    password_hash VARCHAR(128) NOT NULL,   -- bcrypt hash
    created_at  TIMESTAMP DEFAULT NOW(),
    updated_at  TIMESTAMP DEFAULT NOW(),
    last_login  TIMESTAMP,
    login_count INTEGER DEFAULT 0
);

-- 会话记录表（用于Token黑名单和活跃会话管理）
CREATE TABLE sessions (
    id          SERIAL PRIMARY KEY,
    user_id     INTEGER REFERENCES users(id),
    token_jti   VARCHAR(36) NOT NULL UNIQUE,  -- JWT jti claim
    refresh_jti VARCHAR(36) NOT NULL UNIQUE,
    ip_address  VARCHAR(45),
    user_agent  TEXT,
    created_at  TIMESTAMP DEFAULT NOW(),
    expires_at  TIMESTAMP NOT NULL,
    revoked     BOOLEAN DEFAULT FALSE
);
CREATE INDEX idx_sessions_token_jti ON sessions(token_jti);
CREATE INDEX idx_sessions_refresh_jti ON sessions(refresh_jti);
CREATE INDEX idx_sessions_user_id ON sessions(user_id);
```

**技术实现：** FastAPI + `python-jose`(JWT) + `passlib`(bcrypt) + 前端路由守卫 + axios拦截器。约300行代码（后端）+ 200行代码（前端）。

### 4.7 Hermes自我进化系统

#### 4.7.1 核心闭环

```
每次操作结束
    → 归档为结构化经验（市场状态 + 操作 + 结果）
    → 写入经验库
    → Agent检测到规则不适用时写入 feedback.log
    → 每周日自动统计反馈
        → 规则过严 → 生成降门槛建议（推送微信，人工确认后生效）
        → 规则过松 → 生成升门槛建议（推送微信，人工确认后生效）
    → 月度参数迭代（回测验证 + 人工审批）
    → 经验库持续增长 → 场景识别更精准 → 胜率提升
```

> **重要变更：** "自动调参"改为"自动建议+人工审批"。系统生成调参建议并推送到微信，用户确认后才应用。理由：
> - 避免自动调参过拟合近期市场风格
> - 防止级联失败（自动调参→参数变化→策略行为变化→更多失败→更多调参）
> - 保留人工决策的最终否决权

**参数变更安全规则（新增）：**

| 规则 | 说明 |
|:-----|:-----|
| 参数变更必须记录 | 写入 `param_change_log` 表，含变更前后值和变更原因 |
| 自动回测验证 | 每次调参后自动跑7天回测，回测不达标则自动回滚 |
| 变更频率上限 | 同一参数7天内只能调整1次 |
| 人工审批必须 | 系统只出建议，推送微信后用户回复确认才生效 |

#### 4.7.2 冷启动策略

- 系统上线时自动拉取过去2个周期的K线+量价数据
- 标注关键节点价格，关联宏观事件做归因分析
- 快速建立初始经验库
- 第一阶段先跑纯规则模式，Agent做旁路学习（只分析不出手）
- 积累3个月经验样本后，开启Agent辅助决策

**经验库冷启动阶段设计（新增）：**

经验库在样本量不足时，"智能相似度匹配"的效果不可靠。核心价值在冷启动期是统计规律，而非单条经验匹配。

| 阶段 | 经验数量 | 经验法官的工作模式 | 匹配方式 |
|:-----|:---------|:-------------------|:---------|
| **冷启动期** | 0-100条 | 统计分析师：按策略/板块/市场状态统计历史胜率 | 不做单条匹配，只出统计数据 |
| **成长积累期** | 100-2000条 | 统计为主+匹配为辅：统计结果作为权重参考，匹配结果作为补充 | 开始启用相似度匹配，但权重低于统计 |
| **成熟期** | >2000条 | 匹配为主+统计为辅：相似度匹配作为主要判断，统计数据作为校验 | 全面启用相似度匹配 |

> **冷启动阈值从500调至100的理由：** 系统每天最多产生3笔交易，按500条计算需8.3个月才能走出冷启动期，经验法官匹配功能形同虚设。100条约1.5个月即可积累，统计模式已能提供有价值的参考。

**冷启动期经验法官的输出示例：**
```
📊 冷启动期统计报告
━━━━━━━━━━━━━━━━━━━━━━━━
经验总数：128条

按策略统计：
  策略一（底部量能异动）：38笔，胜率47.4%，平均盈亏+2.3%
  策略二（趋势动量低吸）：90笔，胜率58.9%，平均盈亏+4.1%

按市场状态：
  主线行情期间：胜率63.2%（38笔）
  震荡市期间：胜率52.6%（57笔）
  非主线期间：胜率40.9%（33笔）

按板块：
  商业航天：12笔，胜率66.7%
  半导体：18笔，胜率61.1%
  ...（其余板块）

结论：当前策略二在主线行情中表现最好，建议优先选择主线板块的标的。
━━━━━━━━━━━━━━━━━━━━━━━━
```

**技术实现：** 冷启动期经验法官仍然使用LLM，但其提示词改为引导其生成统计报告而非相似度匹配结果。约50行提示词修改。统计查询基于经验表SQL聚合计算。

**回测经验预填充（新增 — 加速冷启动）：**

系统上线前用3年历史数据回测，将回测结果批量写入经验库，大幅缩短冷启动期：

```
系统上线前：
  → 用过去3年历史数据跑两套策略的回测
  → 将回测中的每一笔交易自动转为结构化经验
  → 每笔经验包含：市场状态 + 操作 + 盈亏结果 + 板块 + 策略类型
  → 预计可预填充 200-500 条经验，直接越过冷启动期
  → 预填充经验标记 source='backtest'，与实盘经验区分
```

**冷启动期统计规则自动提取（新增）：**

冷启动期不做单条经验匹配，改为统计规则提取模式：
- 统计胜率最高的板块+策略组合 → 自动生成为"规则型经验"（if-then格式）
- 统计亏损最多的市场状态 → 自动生成"回避规则"
- 规则型经验可被经验法官直接引用，不依赖相似度匹配

### 5.3 API接口设计

#### 5.3.1 API鉴权方案

> 个人系统，无需OAuth2完整流程，采用JWT Bearer Token + 单用户
> 完整认证API清单见 4.6.2.7 节

| 端点 | 方法 | 是否需要鉴权 | 说明 |
|:-----|:-----|:-----------:|:-----|
| `/api/v1/auth/status` | GET | ❌ | 系统是否已初始化 |
| `/api/v1/auth/init` | POST | ❌ | 首次启动初始化（仅调一次） |
| `/api/v1/auth/login` | POST | ❌ | 登录获取Token |
| `/api/v1/auth/refresh` | POST | 需Refresh Token | Token续期 |
| `/api/v1/auth/logout` | POST | ✅ Bearer Token | 登出，使Token失效 |
| `/api/v1/auth/password` | PUT | ✅ Bearer Token | 修改密码 |
| `/api/v1/auth/session` | GET | ✅ Bearer Token | 当前会话信息 |
| 其余所有 `/api/v1/*` 端点 | - | ✅ | 需Bearer Token |

**Token数据结构：**
```json
// Access Token (24h有效期)
{
  "sub": "admin",
  "exp": 1746000000,
  "iat": 1745913600,
  "type": "access",
  "jti": "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
}

// Refresh Token (7天有效期)
{
  "sub": "admin",
  "exp": 1746432000,
  "iat": 1745913600,
  "type": "refresh",
  "jti": "f0e1d2c3-b4a5-6789-0abc-def123456789"
}
```

> 注意：Token中增加了 `jti`（JWT ID）字段，用于会话管理和Token黑名单。

**鉴权流程：**
```
前端请求 /api/v1/*
  → 后端 JWT中间件 校验 Authorization header
  → Token有效 → 检查 Redis 中 jti 是否被撤销
    → 未撤销 → 放行
    → 已撤销 → 返回 401
  → Token过期 → 返回 401
  → 前端自动用 Refresh Token 调用 /auth/refresh
  → 续期成功 → 重新发送原请求
  → 续期失败 → 跳转登录页
  → 登录失败5次 → 返回 429（15分钟锁定）
```

#### 5.3.2 后端API路由

> **注意：** 所有API由API Server(:8000)统一路由分发，不暴露内部端口。策略引擎/Agent调度/交易执行为Scheduler进程内部模块，不独立部署。

| 路由 | 所属模块 | 说明 |
|:-----|:---------|:-----|
| `/api/v1/auth/*` | API Server | 登录、Token管理、系统初始化 |

| `/api/v1/agent/*` | Scheduler进程内部 | Agent运行、讨论记录、权重配置 |
| `/api/v1/trade/*` | API Server | 下单、持仓、交易记录、风控 |
| `/api/v1/market/*` | API Server | 行情/新闻/宏观数据查询 |
| `/api/v1/portfolio/*` | API Server | 资产查询、净值曲线、绩效分析 |

- **`agent_logs`** — Agent分析记录表（每位Agent每日每只标的的分析原文）
- **`experience`** — 经验库表（场景+操作+结果+信心分）
- **`macroeconomic`** — 宏观经济指标表（CPI/PMI/社融等）
- **`users`** — 用户表（仅1行，单用户系统）

**关键索引与分区策略（新增 — 保障查询性能）：**

### 6.1 回测引擎：vnpy.alpha.BacktestingEngine

| 项目 | A股适配度 | 许可证 | 社区活跃 | 上手难度 | 适合场景 |

| Qlib | ⭐⭐⭐ | MIT ✅ | ⭐⭐⭐⭐⭐ | ⭐⭐ | AI因子研究（不适合CTA） |
| Backtrader | ⭐⭐⭐ | GPL ⚠️ | ⭐⭐⭐⭐ | ⭐⭐⭐ | 全球回测（无A股支持） |

**选型理由：**

## 7. 风险与应对方案

> 来源：PRD第9章（经过适配）

### 7.1 技术风险

| 风险点 | 应对方案 |
|:-------|:---------|
| miniQMT接口变更 | 封装接口适配层，接口变更时仅需修改适配层，不影响核心策略与Agent系统 |
| **miniQMT误操作（模拟/实盘混淆）** | **增加交易模式三态开关：SIMULATION / PAPER / LIVE，切换需二次确认。默认启动为模拟盘。LIVE模式下单日/单笔最大金额硬编码限制，不可通过配置绕过** |
| 数据源接口失效 | 多数据源备份机制（miniQMT xtdata → AKShare → 聚宽），一个失效自动切换 |
| 系统崩溃 | 进程监控与自动重启，崩溃后自动恢复策略运行，未完成订单自动重试 |
| 网络断开 | 断网重连机制，恢复后自动同步数据与订单状态 |
| LLM Agent分析误判或API故障 | 1. Agent定位为可插拔增强组件，非系统核心依赖，LLM API故障时自动降级到纯规则模式运行（粗筛+评分+权重排序） 2. 证伪机制（必须输出反对理由） 3. Agent Confidence评分低于阈值时仅记录不下单 4. 规则引擎始终是最终决策 |
| 经验库膨胀 | 设置经验衰减机制，超过6个月的旧经验权重降低，3个月以上未验证的旧经验归档 |
| Redis/数据库故障 | 主从备份，故障时自动切到只读模式确保数据安全 |

### 7.2 交易风险

| 风险点 | 应对方案 |
|:-------|:---------|
| 策略失效 | 自动复盘机制，胜率<50%连续3日自动暂停交易，Agent分析失效原因 |
| 极端行情 | 应急风控机制，大盘单日跌幅≥5%自动清仓暂停3日，账户回撤达标自动降仓 |
| 滑点冲击 | 严格下单量控制，单票买入不超过前5分钟成交额的3%，控制冲击成本 |
| 过拟合 | 样本外验证与参数扰动测试，确保策略的稳健性 |
| 舆情事件处置不及时 | 盘中15分钟轮询，重大事件即时触发告警与处置 |

## 9. 新增建议模块（03-深度分析补充）

> 以下模块在原始需求中未覆盖，但对系统可靠性和可维护性至关重要。

### 9.1 灾备方案

> 原有方案仅有pg_dump每日本地备份，缺少异地灾备

| 措施 | 说明 |
|:-----|:-----|
| 云存储备份 | pg_dump备份同时上传到云存储（阿里云OSS/腾讯COS，每月几块钱） |
| WAL归档 | 数据库WAL归档，支持PITR（时间点恢复） |
| 备份验证 | 每周一次全量备份验证（恢复到测试库确认可用） |

### 9.2 API限流

> 虽为单用户系统，但LLM API有并发限制（如DeepSeek限制5 QPS）

- FastAPI中间件加全局限流：每个IP每秒最多5次请求
- 防止前端误操作快速刷新触发LLM API限流

### 9.3 配置热更新

> 策略参数、风控阈值等配置修改后，需要重启服务才生效

- 关键配置存入PostgreSQL的 `system_config` 表
- 修改配置后通过Redis pub/sub通知各进程
- 进程收到通知后重新加载配置，无需重启

**system_config 表结构：**

```sql
CREATE TABLE system_config (
    key         VARCHAR(64) PRIMARY KEY,
    value       JSONB NOT NULL,
    description TEXT,
    updated_at  TIMESTAMP DEFAULT NOW(),
    updated_by  VARCHAR(32) DEFAULT 'system'
);
```

### 9.4 回测与实盘对比验证

> 回测和实盘是两个独立模块，缺少偏差对比机制

- 每月自动生成"回测vs实盘偏差报告"
- 偏差超过阈值（如实际胜率低于回测胜率20%+）时自动告警
- 偏差数据作为Agent调参建议的输入之一

### 9.5 LLM Token成本监控

> Agent分析成本约10-20元/月，但没有实际Token用量监控机制

- 在 `llm_client` 中增加token计数器，每次调用记录 `prompt_tokens` + `completion_tokens`
- 每日汇总写入 `llm_usage` 表
- 设置日/月Token预算上限，超限自动降级（减少Agent讨论轮数或跳过部分标的）
- 前端设置页增加LLM用量看板

**llm_usage 表结构：**

```sql
CREATE TABLE llm_usage (
    id              SERIAL PRIMARY KEY,
    date            DATE NOT NULL,
    model           VARCHAR(32) NOT NULL,
    agent_name      VARCHAR(32),
    prompt_tokens   INTEGER DEFAULT 0,
    completion_tokens INTEGER DEFAULT 0,
    total_cost      DECIMAL(10,4) DEFAULT 0,
    call_count      INTEGER DEFAULT 1,
    created_at      TIMESTAMP DEFAULT NOW()
);
```
