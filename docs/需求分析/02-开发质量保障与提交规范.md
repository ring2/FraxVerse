# 量化交易系统 —— 开发质量保障与提交规范

> 版本：v1.0  
> 适用范围：本项目所有代码开发  
> 原则：测试先行、小步提交、质量门禁、持续集成

---

## 一、核心理念

```
每条规则都有其存在的原因。不理解原因就去遵守，是盲从；
理解了原因不遵守，是愚蠢。
```

### 1.1 为什么要有这套规范？

- **用户6年交易经验的核心教训**：交易中随手单是亏损根源；开发同理，随手改代码是bug根源
- **量化系统的特殊性**：一个因子错误可能导致实盘亏损，测试不是可选项而是必需品
- **INTJ式工程洁癖**：没人比你更讨厌低质量代码出现在自己的项目里
- **长期主义**：每次偷懒省下的时间，会在后期以10倍时间偿还

### 1.2 开发工作流的根本原则

| 原则 | 说明 |
|------|------|
| **测试先行** | 写代码前先定义"什么算完成"（测试用例） |
| **小步提交** | 一个独立可验证功能点 = 一次提交 |
| **红-绿-重构** | 先让测试红（未通过）→ 实现代码让它绿 → 重构优化 |
| **门禁通关** | pre-commit + CI 不通过 = 代码不可合并 |
| **零妥协** | 测试覆盖率不允许下降，功能性bug必须加回归测试 |

### 1.3 工作流全景图

```
┌─────────────────────────────────────────────────┐
│  1. 拆功能点                                      │
│  将一个需求拆成多个独立可验证的「功能点」               │

                     ▼

│  - 单元测试：mock 数据源，测单一函数逻辑              │

┌─────────────────────────────────────────────────┐
```

## 三、测试分层规范

### 3.1 单元测试（UT）

**目标**：验证单个函数/类的逻辑正确性  
**数量**：最多，覆盖所有非trivial逻辑  
**规则**：

| 规则 | 说明 |
|------|------|
| 隔离 | mock 所有外部依赖（数据库、网络、QMT接口、行情源） |
| 速度 | 单文件测试跑完 < 5秒 |
| 边界 | 测试空值、异常输入、极限值、边界值 |
| 一个断言 | 最好一个测试函数测一个行为 |
| 命名 | `test_<函数名>_<场景>_<预期结果>` |

**示例：**

```python
# tests/unit/test_strategy/test_bottom_volume.py

import pytest
from datetime import datetime
from src.strategy.bottom_volume import detect_washout_bottom


class TestDetectWashoutBottom:
    """周期底部量能异动策略 - 最后洗盘阶段检测"""

    def test_正常洗盘模式_应返回信号(self):
        """给定：底部震荡→暴力下杀→缩量止跌→无利空
        预期：返回买入信号"""
        kline = load_fixture("washout_bottom_normal.csv")
        result = detect_washout_bottom(kline)
        assert result.signal == "BUY"
        assert result.confidence > 0.7

    def test_无缩量止跌_不返回信号(self):
        """给定：一直在放量下跌
        预期：无信号"""
        kline = load_fixture("continuous_drop.csv")
        result = detect_washout_bottom(kline)
        assert result.signal == "NONE"

    def test_空数据_不崩溃(self):
        """给定：空DataFrame
        预期：静默返回 NONE，不抛异常"""
        import pandas as pd
        result = detect_washout_bottom(pd.DataFrame())
        assert result.signal == "NONE"

    def test_仅1根K线_不崩溃(self):
        """给定：只有1根K线
        预期：不会除零或崩溃"""
        kline = load_fixture("single_candle.csv")
        result = detect_washout_bottom(kline)
        assert result.signal is not None
```

### 3.2 集成测试（IT）

**目标**：验证模块间交互正确性  
**范围**：关键数据流路径  
**规则**：

| 规则 | 说明 |
|------|------|
| 真实接口 | 尽量用真实数据源（但可限定小规模） |
| 关键路径 | 数据获取→策略计算→信号输出→风控校验→执行下单 |
| 慢可接受 | 单文件跑完 < 30秒 |
| 幂等 | 重复执行结果一致 |

### 3.3 策略回测校验（Backtest Validation）

**目标**：验证策略在历史数据上的表现符合预期  
**标准**：

| 指标 | 最低标准 | 说明 |
|------|---------|------|
| 交易次数 | ≥20笔 | 避免统计偶然性 |
| 胜率 | ≥40% | 跟策略风格有关，趋势策略低胜率可接受 |
| 最大回撤 | ≤20% | 对应交易理念"少回撤、活下来" |
| 夏普比率 | ≥0.8 | 调整后收益指标 |
| 收益为正 | 是 | 跑赢同期主要指数为佳 |

**示例：**

```python
# tests/strategy/backtest/test_bottom_volume_backtest.py

def test_周期底部量能策略_回测表现达标():
    """在2023-2024年主板行情中回测，验证策略达标"""
    backtest_result = run_backtest(
        strategy="bottom_volume",
        start="2023-01-01",
        end="2024-12-31",
        stock_pool="沪深300",
    )
    assert backtest_result.trade_count >= 20
    assert backtest_result.win_rate >= 0.4
    assert backtest_result.max_drawdown <= 0.2
    assert backtest_result.sharpe >= 0.8
    assert backtest_result.total_return > 0
```

### 3.4 回归测试（Regression Test）

**触发条件**：

- 修复了一个 bug
- 重构了已有代码
- 添加了新功能可能影响现有逻辑

**要求**：
- 修复bug时，先写一个暴露该bug的测试用例 → 修复 → 新测试+原有全量测试通过 → 提交
- 这保证同一个bug永远不会再次出现

## 四、Git 提交规范

### 4.1 提交频率

```
每完成一个「可独立验证的功能点」→ 立即提交

✅ 一个测试通过
✅ 一个策略因子实现
✅ 一个UI页面渲染完成
✅ 一个API端点可调用
✅ 一个bug修复 + 回归测试

❌ "写了半天代码，下班前一起提交"
❌ "功能还在开发中，先不提交"
```

### 4.2 Commit Message 格式

```
<type>(<scope>): <简短描述>

<可选: 详细说明>
```

**类型（type）：**

| Type | 含义 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat(strategy): 实现周期底部量能异动策略` |
| `fix` | 修复bug | `fix(data): 修复K线日期解析越界问题` |
| `test` | 添加/修改测试 | `test(strategy): 补充底部量能策略边界测试` |
| `refactor` | 重构 | `refactor(risk): 抽离止损线计算为独立模块` |
| `docs` | 文档 | `docs: 添加API接口文档` |
| `chore` | 构建/工具 | `chore: 配置pytest-cov覆盖率报告` |
| `perf` | 性能优化 | `perf(data): 优化K线批量读取性能` |
| `style` | 代码格式 | `style: 调整import顺序，无逻辑变更` |

**scope（范围，可选）：**

| Scope | 所属模块 |
|-------|---------|
| `data` | 数据获取、清洗、存储 |
| `strategy` | 策略逻辑 |
| `risk` | 风控模块 |
| `execution` | 交易执行 |
| `agent` | Agent 分析模块 |
| `ui` | 界面 |
| `backtest` | 回测引擎 |
| `api` | 后端API |

### 4.3 完整提交示例

```bash
# ✅ 好的提交
git commit -m "feat(strategy): 实现周期底部量能异动策略的信号生成

基于量价分析和主力行为学，实现4个检测：
1. 底部震荡磨低阶段识别
2. 暴力下杀阶段检测（量能异动）
3. 缩量止跌判断
4. 无利空消息校验入口

Closes #12"

# ✅ 好的提交（修复bug + 回归测试）
git commit -m "fix(data): 修复除权除息日K线复权计算错误

复权因子读取了昨日的收盘价作为基准，导致停牌股复牌日
复权数据异常。修复为使用前复权的标准算法。

新增回归测试 test_exception_right_price_regression"

# ❌ 坏的提交
git commit -m "修复bug"
git commit -m "改了一些东西"
git commit -m "wip"
git commit -m "修复了xxx功能的问题并且优化了性能同时修改了文档"  # 太多职责
```

### 4.4 分支策略

```
main        → 稳定版本，只合入经过CI验证的代码
  │
  └── dev   → 日常开发主分支
       │
       ├── feat/bottom-volume-strategy   → 功能分支
       ├── fix/kline-date-parse           → 修复分支
       └── refactor/risk-module           → 重构分支

原则：
- 功能分支开发 → 测试通过 → PR到dev → CI绿 → merge
- dev持续集成通过后 → 合并到main发版
- 永远不要在main上直接开发
```

## 五、工具链配置

### 5.1 pytest 配置（pytest.ini）

```ini
[pytest]
testpaths = tests
python_files = test_*.py
python_functions = test_*
markers =
    unit: 单元测试，需要快速执行
    integration: 集成测试，可能依赖外部服务
    backtest: 策略回测，执行时间较长
    slow: 耗时的测试（>30秒）
    regression: 回归测试
addopts =
    -v
    --strict-markers
    --tb=short
    -p no:cacheprovider
    --maxfail=5
```

### 5.2 pre-commit 配置（.pre-commit-config.yaml）

> **优化说明：** pre-commit只做快速检查（ruff + 格式化 + 基础检查），pytest和mypy移到push阶段和CI中运行。原配置在每次commit时运行pytest+mypy可能耗时30秒+，严重影响开发体验。

```yaml
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.5.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-yaml
      - id: check-added-large-files  # 默认限制 500KB
      - id: detect-private-key

  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.3.0
    hooks:
      - id: ruff
        args: [--fix, --exit-non-zero-on-fix]
      - id: ruff-format

  # 重检查放到push阶段，不阻塞每次commit
  - repo: local
    hooks:
      - id: pytest-unit
        name: 运行单元测试（push阶段）
        entry: pytest tests/unit -v --tb=short --maxfail=3
        language: system
        pass_filenames: false
        always_run: true
        stages: [push]

      - id: mypy
        name: 类型检查（push阶段）
        entry: mypy src/
        language: system
        pass_filenames: false
        always_run: true
        stages: [push]
```

> **变更原因：** 原配置在commit阶段运行pytest+mypy，合计可能耗时30秒+，严重影响开发体验。改为：commit阶段只做ruff格式检查（<2秒），push阶段才运行pytest+mypy。CI中仍然全量运行。

### 5.3 GitHub CI 配置（.github/workflows/ci.yml）

```yaml
name: Quant System CI

on:
  push:
    branches: [main, dev, 'feat/**', 'fix/**']
  pull_request:
    branches: [main, dev]

jobs:
  test:
    runs-on: ubuntu-latest

    strategy:
      matrix:
        python-version: ["3.11"]

    steps:
      - uses: actions/checkout@v4

      - name: 设置 Python ${{ matrix.python-version }}
        uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}

      - name: 安装依赖
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements-dev.txt

      - name: 代码格式检查
        run: ruff check --output-format=github .

      - name: 类型检查
        run: mypy src/ --ignore-missing-imports

      - name: 单元测试 + 覆盖率
        run: |
          pytest tests/unit -v \
            --cov=src \
            --cov-report=xml \
            --cov-report=term-missing \
            --junitxml=junit.xml \
            -m "not slow"
        env:
          COVERAGE_THRESHOLD: 80

      - name: 集成测试
        run: pytest tests/integration -v --tb=short
        continue-on-error: true  # 集成测试失败不阻塞（环境差异）

      - name: 上传覆盖率报告
        uses: codecov/codecov-action@v4
        with:
          file: coverage.xml
          fail_ci_if_error: false

  quality-gate:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - name: 质量门禁通过
        run: echo "✅ 所有检查通过，代码可合并"
```

### 6.3 模拟洗盘场景的数据生成器

对于策略测试，需要构造**特定的量价形态**（比如洗盘底部的量价模式）。我会提供一个辅助函数：

```python
# tests/fixtures/generate_scenario.py

import numpy as np
import pandas as pd

def generate_washout_bottom_scenario(
    days=120,
    seed=42
) -> pd.DataFrame:
    """
    生成「底部震荡→暴力下杀→缩量止跌」的模拟K线
    - Phase 1 (1-60天): 底部震荡磨低，量能逐渐萎缩
    - Phase 2 (61-70天): 暴力下杀，放量恐慌
    - Phase 3 (71-100天): 缩量止跌，最后一跌
    - Phase 4 (101-120天): 企稳回升，量能温和放大
    """
    rng = np.random.default_rng(seed)
    close = np.zeros(days)
    volume = np.zeros(days)

    # Phase 1: 底部震荡（缓慢下跌）
    close[:60] = 10.0 * (1 - 0.001 * np.arange(60)) + rng.normal(0, 0.02, 60)
    volume[:60] = 100 + rng.normal(0, 10, 60)

    # Phase 2: 暴力下杀
    close[60:70] = close[59] * (1 - 0.025 * np.arange(1, 11)) + rng.normal(0, 0.01, 10)
    volume[60:70] = 300 + rng.normal(0, 20, 10)

    # Phase 3: 缩量止跌
    close[70:100] = close[69] + rng.normal(0, 0.005, 30)
    volume[70:100] = 30 + rng.normal(0, 5, 30)

    # Phase 4: 企稳
    close[100:] = close[99] * (1 + 0.003 * np.arange(1, 21)) + rng.normal(0, 0.01, 20)
    volume[100:] = 80 + rng.normal(0, 10, 20)

    df = pd.DataFrame({
        "date": pd.date_range("2024-01-01", periods=days, freq="D"),
        "open": close * (1 + rng.normal(0, 0.002, days)),
        "high": close * (1 + abs(rng.normal(0, 0.003, days))),
        "low": close * (1 - abs(rng.normal(0, 0.003, days))),
        "close": close,
        "volume": volume,
        "amount": volume * close * 100,
        "turnover_rate": volume / 10000,
    })
    return df.round(2)
```

## 八、数据库迁移规范（Alembic）

### 8.1 为什么需要数据库迁移工具？

量化系统的数据库schema变更频繁（新增因子、修改经验库结构、增加配置表等），没有迁移工具会导致：
- 生产数据丢失
- 开发/测试/生产环境schema不一致
- 无法回滚错误的schema变更

### 8.2 Alembic 使用规范

| 规则 | 说明 |
|:-----|:-----|
| 每次schema变更必须生成migration | `alembic revision --autogenerate -m "描述"` |
| 生产环境禁止直接修改数据库 | 必须通过 `alembic upgrade head` |
| migration脚本必须纳入版本控制 | 与代码一起提交到git |
| CI中加入migration测试 | 从空库 → 运行所有migration → 验证schema正确 |
| 回滚前必须备份 | `pg_dump` → `alembic downgrade -1` |

### 8.3 常用命令

```bash
# 生成迁移脚本（自动检测model变化）
alembic revision --autogenerate -m "add market_state_log table"

# 执行迁移到最新版本
alembic upgrade head

# 回滚一个版本
alembic downgrade -1

# 查看当前版本
alembic current

# 查看迁移历史
alembic history

# 从空库开始运行所有迁移（CI测试用）
alembic upgrade head
```

### 8.4 CI中的migration测试

```yaml
# 在 .github/workflows/ci.yml 中增加
- name: 数据库迁移测试
  run: |
    createdb quant_test
    alembic -x db_url=postgresql://localhost/quant_test upgrade head
    pytest tests/ -k "migration" -v
```

## 九、常见陷阱与最佳实践

### 9.1 量化系统测试的特殊陷阱

| 陷阱 | 说明 | 如何避免 |
|------|------|---------|
| **幸存者偏差** | 测试只用了存活至今的股票数据 | 使用全量历史数据（含已退市股票） |
| **前视偏差** | 测试时使用了未来数据（如当日收盘价） | 数据时间戳严格校验，use `pytest-time-machine` |
| **过拟合** | 策略参数针对测试数据调优 | 样本内/样本外划分（8:2），参数不变跑样本外 |
| **忽略交易成本** | 测试不考虑印花税、滑点 | mock 交易执行时加入 0.1% 滑点 + 0.1% 手续费 |
| **并行测试冲突** | 多个测试同时写同一个数据库 | 使用临时数据库或 in-memory SQLite |
| **浮点精度** | 金融计算中的浮点误差被放大 | 金额用 Decimal 或放大为整数分 |

### 9.2 每日开发结束检查清单

```
□ 当前分支所有测试通过
□ ruff 无错误
□ mypy 无类型错误
□ 今天提交了（至少1次）
□ CI 绿色（如果已推送）
□ 如果提交了但 CI 还在跑，记得明天早上看一眼
```

### 9.3 一句话铁律

> **测试没通过 = 功能没完成。CI没绿 = 合入即事故。**
