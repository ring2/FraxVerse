## 1. 第一性原理拆解

### 1.1 系统的不可再分公理

经过三轮第一性原理追问，系统可以拆解为以下**不可再分的公理组**：

```
公理一：市场不可预测，只能提高概率
  → 系统不追求"预测正确"，追求"长期正期望值"
  → 核心指标：盈亏比 × 胜率 - 亏损比 × (1-胜率) > 0

公理二：信息可以获取，但解读有成本
  → 公开信息对所有参与者相同
  → 解读能力决定差异
  → LLM的解读成本低于人工，这是系统相对于散户的优势所在

公理三：执行纪律是散户最大的软肋
  → 情绪化决策（扛单、追涨、杀跌等）的损失 > 信息劣势的损失
  → 系统的核心价值是纪律执行，不是信息获取

公理四：系统必须能自我纠错
  → 人设计的系统一定存在盲区
  → 必须有一种机制让系统在运行中自动发现和纠正错误
  → 不能依赖开发者手动调参

公理五：复杂度不创造价值，正确性创造价值
  → 越复杂的系统，bug越多，越难调试
  → 每一行代码都要回答一个问题：没有它，系统会不会崩溃？
```

### 1.2 由公理推导出的架构原则

| 公理 | 推导出的架构原则 |
|:-----|:-----------------|
| 公理一 | 纯规则模式是系统基线，Agent是增强组件（可热插拔） |
| 公理二 | LLM调用设计为异步非阻塞，超时自动降级 |
| 公理三 | 止损进程独立于主系统运行，不受任何其他模块影响 |
| 公理四 | 所有AI判断都有校准机制，所有规则都有自动调参建议路径（人工审批后生效） |
| 公理五 | 容器化部署 + 微服务隔离，故障范围最小化 |

### 2.3 进程模型

系统共包含**4个常驻进程 + N个定时任务**：

```
┌──────────────────────────────────────────────────────────────┐
│                       docker-compose 编排                      │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  进程1: API Server （main.py）                                 │
│  ├── FastAPI Web Server (:8000)                              │
│  ├── WebSocket 连接管理                                       │
│  ├── 路由分发（auth/strategy/trade/market/...）                │
│  └── 生命周期：常驻                                           │
│                                                              │
│  进程2: Scheduler（定时任务）                                   │
│  ├── 每日收盘后工作流（15:30）：数据采集 → 筛选 → Agent → 投票  │
│  ├── 开盘前决策复核（9:00）                                    │
│  ├── 盘中舆情采集（每小时）                                    │
│  ├── 账户同步（每5分钟）                                      │
│  ├── 每周复盘 + 月度报告                                      │
│  └── 生命周期：常驻                                           │
│                                                              │
│  进程3: Stop-Loss Monitor（止损监视器 — 独立容器 🛡️）         │
│  ├── 独立Docker容器运行（不与backend同容器）                   │
│  ├── 启动时从PG加载所有active止损条件到内存                    │
│  ├── 盘中只从Redis读取实时行情（不每秒查PG）                   │
│  ├── 新开仓通过Redis pub/sub通知更新内存                      │
│  ├── 每秒检查持仓止损条件                                      │
│  ├── 触发时直接执行卖出（不经过API Server）                     │
│  ├── restart: always（崩溃自动重启，最高优先级）               │
│  └── 生命周期：常驻                                           │
│                                                              │
│  进程4: Frontend（前端静态资源服务）                              │
│  ├── Nginx 提供React构建文件                                   │
│  ├── 反向代理 /api/* → API Server                             │
│  └── 生命周期：常驻                                           │
│                                                              │
│  定时任务（由Scheduler进程触发或cron）:                          │
│  ├── 每日数据备份（pg_dump） → 凌晨3:00                        │
│  ├── 经验库归档 → 每周日凌晨2:00                               │
│  └── Agent权重校准（每次投票前） → 触发式                        │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

**为什么是4个进程而不是更多？**

| 曾经考虑过的独立服务 | 为什么合并 | 决策依据 |
|:--------------------|:----------|:---------|
| 独立的数据采集微服务 | 合并到Scheduler进程 | 数据采集是定时触发的，不是实时流的。不需要常驻服务。 |
| 独立的Agent调度服务 | 合并到Scheduler进程 | Agent调度是每日工作流的一部分，不是独立运行的。LLM调用是异步的，不需要独立进程。 |
| 独立的策略引擎微服务 | 合并到Scheduler进程 | 策略引擎只在收盘后运行一次，每秒完成。不需要常驻。 |
| 独立的风控服务 | 合到API Server | 风控检查是同步的、低延迟的，不需要独立部署。 |

**唯一必须独立运行的进程：止损监视器。** 因为它不能依赖其他任何进程，必须在主系统崩溃时仍能工作。因此止损监视器必须作为**独立Docker容器**运行，不能与backend同容器——容器级别的隔离才能确保backend崩溃/OOM/重启时止损仍能工作。

### 3.2 核心模块详细设计

#### 3.2.1 llm_client — LLM调用客户端

```
llm_client/
├── __init__.py
├── client.py          # LLM客户端主类（异步调用 + 超时 + 降级）
├── models.py          # 请求/响应的Pydantic模型
├── config.py          # LLM配置管理（API Key/Base URL/超时/并发）
└── prompts/           # Agent提示词（独立目录便于迭代）
    ├── main_hunter.md
    ├── money_detective.md
    ├── mood_catcher.md
    └── experience_judge.md
```

**功能规格：**

| 功能 | 细节 |
|:-----|:------|
| 异步调用 | `asyncio` + `httpx.AsyncClient` 并发调用，默认并发数8 |
| 超时机制 | 单次调用超时60秒，超时返回None |
| 自动降级 | 主模型失败 → 自动切换备用模型 |
| 重试策略 | 指数退避重试，最多3次 |
| 模型选择 | 日常分析用 DeepSeek V3，关键决策用 Claude Sonnet |
| Token预算 | 每日可配Token上限，超限停止调用 |

**接口定义：**

```python
class LLMClient:
    async def analyze(
        self,
        agent_role: str,        # Agent角色名称
        prompt_key: str,        # 提示词标识
        context: dict,          # 上下文数据
        model_priority: str = "daily"  # "daily" 或 "critical"
    ) -> AgentAnalysis | None:  # None = 超时/失败
        ...
```

#### 3.2.2 stop_loss_monitor — 止损监视器（独立进程）

```
trade/
├── stop_loss_monitor.py   # 独立进程入口
├── stop_loss_config.py    # 止损配置
└── trade_utils.py         # 共享工具函数
```

**架构约束：**

```
┌──────────────────────────────────┐
│       主系统进程（任何进程）        │
│                                  │
│  开仓时：将止损条件写入数据库       │
│  INSERT INTO stop_conditions     │
│  (order_id, stock_code,          │
│   stop_price, status='active')   │
│                                  │
│  同时：通过Redis pub/sub通知       │
│  止损监视器新开仓条件              │
└──────────┬───────────────────────┘
           │ 共享数据库 + Redis pub/sub
           ▼
┌──────────────────────────────────┐
│     止损监视器（独立容器）          │
│                                  │
│  on_startup:                     │
│    从PG加载所有active止损条件      │
│    到内存 active_conditions       │
│                                  │
│  on_new_position (Redis pub/sub):│
│    更新内存中的止损条件            │
│                                  │
│  while True:                     │
│    遍历内存中active条件           │
│    从Redis读取实时行情            │
│    触发条件 → 执行卖出            │
│    更新止损条件状态               │
│    time.sleep(1)                 │
└──────────────────────────────────┘
```

**关键规则：**
- 启动时扫描所有 `status='active'` 的条件，加载到内存
- 每秒循环一次，只从Redis读价格，不查PG（性能优化）
- 新开仓通过Redis pub/sub通知，实时更新内存缓存
- 不读取任何Agent输出、新闻、市场判断
- 通过miniQMT的实时行情接口获取价格
- 被执行过的条件标记为 `triggered`
- 执行记录写入 `trade_logs` 表

#### 3.2.3 agent_orchestrator — Agent编排调度

```
agent/
├── __init__.py
├── orchestrator.py   # Agent编排主逻辑
├── roles.py          # 四位Agent角色定义
├── calibration.py    # Agent在线校准（胜率/权重）
├── templates.py      # 提示词模板
```

**工作流：**

```
1. orchestrator.receive(stock_pool: list[Stock])
   ↓
2. 加载Agent校准数据（从agent_calibration表）
   ↓
3. 并发调用4个Agent × N只股票
   └── llm_client.analyze(role, prompt, context)
   ↓
4. 收集所有Agent输出
   └── 记录到 agent_logs 表（含 predicted_outcome）
   ↓
5. 加权投票（权重 = 基准权重 × 校准系数）
   ↓
6. 风控过滤
   ↓
7. 输出最终决策
```

```
scheduler/
├── __init__.py
```

**每日工作流（最核心）：**

```
15:00 收盘
  │
15:05 (1) 数据采集
  │      ├── miniQMT: 全市场日K线/板块成分股/资金流向
  │      └── AKShare: 补充资金流向/龙虎榜/财务数据
  │
15:10 (2) 粗筛
  │      5000只 → 约50只（规则引擎，秒级）
  │
15:10 (3) 评分
  │      50只 → 前15只入股票池（规则引擎，秒级）
  │
15:11 (4) Agent分析（异步并发）
  │      先分析评分前5只 × 4 Agent = 20次LLM调用
  │      ├── 被否决≤2只 → 直接投票
  │      └── 被否决≥3只 → 从后10只补充3-5只再分析
  │      平均20-40次调用，耗时2-5分钟
  │
15:16 (5) 加权投票 + 风控过滤
  │      最终1-3只精选标的
  │
15:17 (6) 推送微信
  │      Agent精选结果推送
  │
15:18 (7) 归档
  │      当日股票池、Agent分析、最终决策 → 经验库
  │
次日9:00 (8) 开盘前决策复核
         检查隔夜变化 → 高开/低开≥3%取消买入计划
```

```
experience/
├── __init__.py
├── repository.py     # 经验存储/检索
├── matcher.py        # 场景匹配引擎（成熟期启用）
```

**三阶段模式：**

| 阶段 | 条件 | 模式 | 说明 |
|:-----|:-----|:-----|:------|
| 冷启动期 | 经验 < 100条 | 统计模式 | 只做SQL聚合统计（按策略/板块/市场状态），不做智能匹配。100条约1.5个月可积累，统计模式已能提供有价值参考 |
| 成长积累期 | 100-2000条 | 混合模式 | 统计为主+匹配为辅 |
| 成熟期 | > 2000条 | 匹配模式 | 相似度匹配为主+统计校验 |

## 4. 数据流设计

### 4.1 核心数据流：每日交易流程

| LLM API Key | 环境变量（.env） | — | 不存入数据库 |

## 8. 附录：架构决策记录

| ID | 决策 | 时间 | 替代方案 | 原因 |
|:---|:-----|:-----|:---------|:-----|
| ADR-001 | 纯规则模式是系统基线，Agent可插拔 | V1 | Agent必须 | P0不依赖LLM，API故障时自动降级 |
| ADR-002 | 4个进程，非N个微服务 | V1 | 每个模块独立服务 | 个人系统不需要分布式，进程少降低运维复杂度 |
| ADR-003 | 止损监视器独立进程 | V1 | 同进程 | 止损不能依赖主系统 |
| ADR-004 | 状态管理用Zustand | V1 | Redux | 单用户系统，Zustand 1KB vs Redux 12KB |
| ADR-005 | 前端 PC/Mobile 双Layout | V1 | 纯响应式 | 12个复杂页面，纯CSS响应式不够，需要不同组件 |
| ADR-006 | 数据库只用PostgreSQL | V1 | InfluxDB分开 | K线存关系表足够用，减一个依赖少一份运维 |
| ADR-007 | 定时任务用APScheduler（全程，不升级Celery） | V1 | Celery | APScheduler + PostgreSQL jobstore持久化足够个人系统使用，Celery需额外Broker增加运维复杂度 |
| ADR-008 | 回测引擎提取vnpy核心文件 | V1 | 自研/scipy | 6个文件搞定，不引入第三方依赖 |
| ADR-009 | 自动调参改为"建议+人工审批" | V1 | 全自动调参 | 避免过拟合近期市场风格、级联失败、不可逆变更。系统只出建议，人工确认后才生效 |
| ADR-010 | 止损监视器独立Docker容器 | V1 | 同容器3进程合一 | 容器级隔离确保主系统崩溃时止损仍能工作，止损是系统第一安全底线 |
| ADR-011 | pg_dump备份上传云存储 | V1 | 仅本地备份 | 防止硬盘损坏/误删/勒索攻击导致数据不可恢复，OSS/COS每月几块钱 |
| ADR-012 | API全局限流5 QPS | V1 | 无限流 | 防止前端误操作快速刷新触发LLM API限流（DeepSeek 5 QPS限制） |
| ADR-013 | 配置热更新通过Redis pub/sub | V1 | 重启生效 | 盘中调参无需重启服务，修改system_config表后通知各进程重新加载 |
