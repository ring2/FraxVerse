# P0-1 事件驱动重构 · 实施计划

> **目标**：引入基于 Redis Pub/Sub 的事件驱动架构，将 Pipeline 模式的模块调用解耦为事件订阅模式。
> **核心痛点**：止损→通知→风控标记是顺序调用，任何一步失败后续中断。
> **方案轻量**：纯增量，不引入新依赖（已有 Redis 容器），不改现有业务代码。

---

## 一、设计原则

1. **零侵入** — 现有模块的 import 和调用方式不变，新加 EventBus 层作为增量选项
2. **渐进采用** — 先改止损链路（痛点最突出），其他模块保持不动
3. **可观测** — 所有事件发布/消费都有日志，便于调试

---

## 二、架构设计

### 2.1 核心概念

```
发布方                    EventBus                   订阅方
─────────               ─────────                  ─────────
StopLossMonitor  ──→  Redis Pub/Sub  ──→  WeChatNotifier
Scheduler        ──→   事件通道       ──→  RiskLogger
User Action      ──→                 ──→  TradeEngine
```

### 2.2 事件类型定义

```
┌────────────────────────────────────────────────────────┐
│                   EventType 枚举                        │
├────────────────────────────────────────────────────────┤
│ STOP_LOSS_TRIGGERED    止损被触发                      │
│ STOP_PROFIT_TRIGGERED  止盈被触发                      │
│ POSITION_OPENED        新开仓                           │
│ POSITION_CLOSED        清仓离场                         │
│ RISK_ALERT             风控告警（回撤/连续亏损等）       │
│ MARKET_EXTREME         极端行情                         │
│ TRADE_SIGNAL_GENERATED 新交易信号                       │
│ SYSTEM_ERROR           系统级错误                        │
└────────────────────────────────────────────────────────┘
```

### 2.3 事件数据结构

```python
@dataclass
class Event:
    event_type: EventType      # 事件类型
    source: str                # 来源模块名（如 "stop_loss_monitor"）
    timestamp: float           # 事件时间
    data: dict                 # 业务数据（不同事件类型格式不同）
    event_id: str              # 唯一ID（UUID，用于去重）
```

class EventType(Enum):
    STOP_LOSS_TRIGGERED = auto()
    STOP_PROFIT_TRIGGERED = auto()
    POSITION_OPENED = auto()
    POSITION_CLOSED = auto()
    RISK_ALERT = auto()
    MARKET_EXTREME = auto()
    TRADE_SIGNAL_GENERATED = auto()
    SYSTEM_ERROR = auto()

@dataclass
class Event:
    event_type: EventType
    source: str
    timestamp: float
    data: dict
    event_id: str = field(default_factory=lambda: uuid.uuid4().hex[:12])

## 四、风险与注意事项

| 风险 | 影响 | 预防 |
|:-----|:----|:-----|
| Redis 连接断开 → 事件丢失 | 推送/风控漏记 | EventBus 默认 log warning 不抛异常，不影响核心交易逻辑 |
| Pub/Sub 无持久化 → 重启后事件丢失 | 重启期间的止损不推送 | 可接受，已有 RiskEvents 表记录止损本身 |
| 事件循环阻塞 → 消费延迟 | 推送延迟 | 每个订阅者在独立协程运行 |
| 旧模块不动 → 双通路 | 一个事件触发两次通知 | 老接口保留但逐步废弃，优先走事件 |

## 五、后续扩展

- **v2**：引入事件持久化（Redis Stream 替代 Pub/Sub，重启后可回溯丢失事件）
- **v3**：WebSocket 推送到前端（前端实时收到止损/风控告警）
- **v4**：事件日志面板（管理后台查看历史事件流）
